## 1. Identity & Access Management

> **Domain Description:** Covers all authentication, authorization, user lifecycle, and tenant provisioning concerns. Every other domain depends on the identity contracts (`iam/contracts`) exposed by this module. Corresponds to the `iam` Spring Modulith module in the Core Backend and the multi-layer RBAC enforcement described in `docs/system-design.md §5`.

### 1.1 `user-registration-and-identity-verification`

**Description:** Allows a new `STUDENT` to self-register on the platform. Upon registration, the system validates the submitted email against the `student_directory` table (populated by the nightly CSV ingestion pipeline) to establish a verified identity link (`users.student_record_id`). Students whose email cannot be matched to a `student_directory` record are created as accounts but are blocked from registering for workshops until verified. This is the only self-service account creation flow — `ORGANIZER` and `STAFF` accounts are exclusively created by delegated provisioning (see feature `staff-and-organizer-provisioning`).

| Attribute           | Detail                                                                                                                                         |
| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `iam` (primary — user creation, identity verification, `student_record_id` link), `shared/security` (password hashing)                         |
| **Worker Modules**  | None                                                                                                                                           |
| **System Flow Ref** | `docs/system-design.md §5 — Account Provisioning & Security`                                                                                   |
| **ADR Refs**        | ADR-005 (JWT RS256), ADR-006 (RBAC), ADR-028 (Zero-Trust Provisioning)                                                                         |
| **DB Tables**       | `users`, `student_directory`, `organizations`                                                                                                  |
| **Clients**         | Web                                                                                                                                            |
| **Key Constraints** | Password hashed with Argon2/Bcrypt. `student_record_id` is nullable; `NULL` = workshop registration blocked. Email unique via `CITEXT UNIQUE`. |

### 1.2 `authentication-and-session-management`

**Description:** Implements the complete authentication session lifecycle: login with email/password returning a short-lived RS256-signed JWT access token and a long-lived refresh token; access token refresh using the refresh token (with rotation on each use); and secure logout that revokes the JWT's `jti` claim in the Redis blacklist and invalidates the refresh token in the database. Also enforces the mandatory first-login password change for accounts where `is_temporary_password = true` (provisioned `STAFF`/`ORGANIZER` accounts). The JWKS endpoint (`/.well-known/jwks.json`) exposes the RSA public key for token verification by downstream services. On `STAFF` login, the response additionally includes the current RSA public key (in PEM format) to be cached in the mobile app's local SQLite `mobile_public_keys` table for offline QR signature verification (per ADR-029).

| Attribute           | Detail                                                                                                                                                                                                                                                                                                       |
| :------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `iam` (primary — auth use cases, token generation), `shared/security` (JWT RS256 signing/verification, Redis JTI blacklist, JWKS endpoint, public key distribution on `STAFF` login)                                                                                                                         |
| **Worker Modules**  | None                                                                                                                                                                                                                                                                                                         |
| **System Flow Ref** | `docs/system-design.md §5 — RBAC Model & Multi-Layer Enforcement`, `§5 — Offline PKI & Cryptography`                                                                                                                                                                                                         |
| **ADR Refs**        | ADR-005 (JWT RS256 + Redis JTI revocation), ADR-010 (Redis fail-closed for JTI checks), ADR-029 (public key distribution on `STAFF` login)                                                                                                                                                                   |
| **DB Tables**       | `users`, `refresh_tokens`                                                                                                                                                                                                                                                                                    |
| **Clients**         | Web, Mobile                                                                                                                                                                                                                                                                                                  |
| **Key Constraints** | Access token: short-lived (e.g., 1 hour). Refresh token: stored as `token_hash` only, rotated on each use. JTI blacklist is **fail-closed** — Redis unavailability returns `503 Service Unavailable`. On `STAFF` login, response body MUST include the current `public_key_pem` for offline QR verification. |

### 1.3 `public-key-distribution`

**Description:** Provides a dedicated, authenticated `GET /api/v1/auth/public-key` endpoint that returns the current RSA public key in PEM format. This endpoint is the explicit mechanism for the mobile app to refresh its cached public key on demand — for example, after a key rotation event that invalidates previously cached keys. Unlike the JWKS endpoint (which is used for JWT signature verification by downstream services), this endpoint is designed specifically for the mobile `STAFF` client and returns the key in the PEM format that the mobile app can directly store in `mobile_public_keys`. Key rotation invalidates all previously issued QR signatures; staff must fetch the new key on their next online session. Without this endpoint, the mobile app has no mechanism to recover from a key rotation while the app is already authenticated.

| Attribute           | Detail                                                                                                                                                                                                                                               |
| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `shared/security` (primary — RSA key material loading and PEM serialization), `iam` (JWT validation for authentication)                                                                                                                              |
| **Worker Modules**  | None                                                                                                                                                                                                                                                 |
| **System Flow Ref** | `docs/system-design.md §5 — Offline PKI & Cryptography`                                                                                                                                                                                              |
| **ADR Refs**        | ADR-005 (RSA key pair), ADR-029 (PKI QR signing + offline verification, key rotation invalidates all cached keys)                                                                                                                                    |
| **DB Tables**       | None (key material is loaded from `resources/security/public.pem` at startup)                                                                                                                                                                        |
| **Clients**         | Mobile (primary consumer), Web (informational only)                                                                                                                                                                                                  |
| **Key Constraints** | Requires a valid `STAFF` JWT — unauthenticated access is forbidden. Response: `{ key_id, public_key_pem, issued_at }`. Prerequisite for F-6.1 (`mobile-offline-checkin`) and F-6.2 (`attendance-sync-reconciliation`) to function correctly offline. |

### 1.4 `password-reset`

**Description:** Provides a self-service password reset flow for users who have forgotten their credentials. A user submits their email; the system generates a cryptographically random, single-use reset token, stores its hash in `password_reset_tokens` with an expiry TTL, and sends the reset link via the notification worker. On link consumption, the token is validated (non-expired, non-used), the password is updated and hashed, the token is marked as `used_at`, and all active refresh tokens for the user are revoked.

| **System Flow Ref** | `docs/system-design.md §5 — Account Provisioning & Security`                                                                                                    |

| **Clients**         | Web                                                                                                                                                             |
| **Key Constraints** | Tokens are single-use; `used_at` set on first valid consumption. Expired tokens purged by the TTL cleanup job every 6 hours (per `docs/database-schema.md §1`). |

### 1.5 `staff-and-organizer-provisioning`

**Description:** Enables `ORGANIZER` users to create `STAFF` accounts and invite additional `ORGANIZER` accounts within their own organization. Following the Zero-Trust provisioning model (ADR-028), the creating organizer cannot set passwords. The system generates a secure temporary password, emails it directly to the new user, and sets `is_temporary_password = true` to force a mandatory reset on first login. All provisioned accounts are scoped to the same `organization_id` as the creating `ORGANIZER`. `STAFF` users created here have no check-in privileges until explicitly assigned to a workshop via `staff-assignment-management`.

### 1.6 `staff-assignment-management`

**Description:** Enables `ORGANIZER` users to assign `STAFF` members to specific workshops, granting them the ability to perform QR code scanning and attendance synchronization for those workshops. Assignments are tracked in the `workshop_assignments` bridging table. An `ORGANIZER` can also revoke assignments. `STAFF` members can only check in at workshops they are explicitly assigned to — even within the same organization, an unassigned `STAFF` user receives `403 Forbidden` at the check-in endpoint. Organizers can view the current list of staff assigned to a given workshop.

### 1.7 `active-session-management`

**Description:** Provides authenticated users with the ability to view and revoke their active login sessions. Each row in `refresh_tokens` represents one active session and carries `device_info` (User-Agent / device name) and `ip_address` for identification. `GET /api/v1/auth/sessions` returns the paginated list of non-expired, non-revoked sessions. `DELETE /api/v1/auth/sessions/{id}` revokes a specific session by setting `revoked_at` on the `refresh_tokens` row and adding the corresponding access token's `jti` to the Redis blacklist (if the active token for that session is known). `DELETE /api/v1/auth/sessions` (revoke-all) revokes all sessions except the caller's current session. This feature enables users to detect and terminate unauthorized sessions — a standard security control made possible by the existing `device_info` and `ip_address` columns in `refresh_tokens`.

## 2. Workshop Lifecycle Management

> **Domain Description:** Covers the entire server-side management of workshops from creation through terminal states. This is the most complex domain in the system, involving strict state machine enforcement (`DRAFT` → `PUBLISHED` → `COMPLETED`/`CANCELED`), multi-tenant ownership checks, optimistic locking for concurrent edits, automated sweeper-based transitions, and the transactional outbox pattern for reliable event fan-out to Elasticsearch and notification workers. Corresponds to the `workshops` Spring Modulith module and the **Workshop Lifecycle Management Flow** in `docs/system-design.md §4`.

### 2.1 `workshop-creation-and-draft-management`

**Description:** Enables authenticated `ORGANIZER` users to create a new workshop in `DRAFT` status. In `DRAFT`, all fields are fully editable with no restrictions. The workshop is not visible to students, is not indexed in Elasticsearch, and generates no external domain events until it is published. Organizers can update (full field set), preview, and delete `DRAFT` workshops. Deletion of `DRAFT` workshops is the only hard-delete permitted in the system (no registered students, no financial records exist yet). When creating or updating a workshop (in `DRAFT` or `PUBLISHED`), if speakers are included, the system must check whether any speaker email is already committed to another workshop in the same time window (speaker overlap detection). The check queries `workshop_speakers` by `email` and compares the time range against other non-`CANCELED`, non-`DRAFT` workshops. A speaker overlap returns `422 Unprocessable Entity`.

| Attribute           | Detail                                                                                                                                                                                                                                                                                                             |
| :------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `workshops` (primary — CRUD use cases, domain entity, `WorkshopSpeakerRepository`, speaker overlap detection query), `iam/contracts` (org + role validation)                                                                                                                                                       |
| **Worker Modules**  | None (`DRAFT` events never externalized)                                                                                                                                                                                                                                                                           |
| **System Flow Ref** | `docs/system-design.md §4 — Workshop Lifecycle Management Flow (CREATE OPERATION)`                                                                                                                                                                                                                                 |
| **ADR Refs**        | ADR-006 (RBAC + org scoping), ADR-008 (Flyway schema migrations)                                                                                                                                                                                                                                                   |
| **DB Tables**       | `workshops`, `workshop_speakers`, `organizations`                                                                                                                                                                                                                                                                  |
| **Clients**         | Web                                                                                                                                                                                                                                                                                                                |
| **Key Constraints** | `status = DRAFT` on creation. `organization_id` set from `jwt.org`. `version = 0` initialized for optimistic locking. No outbox events emitted for `DRAFT` changes. Speaker overlap check uses `idx_workshop_speakers_email` index on `workshop_speakers.email`. Returns `422` on any speaker scheduling conflict. |

### 2.2 `workshop-publishing-and-update`

**Description:** Manages the `DRAFT` → `PUBLISHED` state transition (publishing) and the rules governing updates to a `PUBLISHED` workshop. Publishing triggers a `WorkshopPublishedEvent` into the transactional outbox. This event is externalized by the Spring Modulith Event Registry to RabbitMQ, and the `search_sync` background worker consumes it to index the workshop in Elasticsearch — this is the mechanism by which a newly published workshop becomes searchable. Once published, core immutable fields (e.g., `price`, `currency`) cannot be changed, and `capacity` cannot be reduced below the current `CONFIRMED` + `PENDING` registration count. Non-core fields (e.g., `description`, `cover_image_url`) remain editable and emit a `WorkshopUpdatedEvent` for Elasticsearch re-synchronization via the same outbox → RabbitMQ → `search_sync` worker path. Optimistic locking (`@Version`) prevents lost updates from concurrent organizer edits, returning `409 Conflict` on version mismatch.

| **Backend Modules** | `workshops` (primary — state machine, optimistic locking, outbox publication), `shared/events` (outbox infrastructure)                                                                                                                                                                                                  |
| **Worker Modules**  | `search_sync` (consumes `WorkshopPublishedEvent` and `WorkshopUpdatedEvent` from RabbitMQ to upsert Elasticsearch index)                                                                                                                                                                                                |
| **System Flow Ref** | `docs/system-design.md §4 — Workshop Lifecycle Management Flow (PUBLISH OPERATION, UPDATE OPERATION, ASYNCHRONOUS EVENT FAN-OUT)`                                                                                                                                                                                       |
| **ADR Refs**        | ADR-006 (ownership validation `jwt.org == workshop.organization_id`), ADR-012 (ES CQRS), ADR-013 (optimistic locking via `@Version`), ADR-017 (RabbitMQ broker), ADR-018 (Transactional Outbox)                                                                                                                         |
| **DB Tables**       | `workshops`, `event_publication`                                                                                                                                                                                                                                                                                        |

### 2.3 `workshop-rescheduling`

**Description:** Allows `ORGANIZER` users to reschedule a `PUBLISHED` workshop to a new future time slot. The reschedule endpoint is explicitly restricted to `PUBLISHED` workshops — `DRAFT`, `COMPLETED`, and `CANCELED` states return `422`. The system validates that the new time range is valid (start < end, both in the future) and performs a PostgreSQL-level resource collision check to ensure the target location and any assigned speakers are not already committed to another workshop in the proposed time window. Speaker overlap uses the `email` index on `workshop_speakers`. On success, a `WorkshopRescheduledEvent` is emitted via the outbox, triggering Elasticsearch re-sync (via RabbitMQ → `search_sync` worker) and bulk notification to all registered students (via RabbitMQ → `notifications` worker). Cache invalidation: the Redis search cache key for this workshop's affected queries must be invalidated so the SWR cache reflects the rescheduled time immediately.

| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **Worker Modules**  | `search_sync` (ES update via RabbitMQ), `notifications` (bulk email/push to registered students via RabbitMQ)                                                                                                                                                    |
| **System Flow Ref** | `docs/system-design.md §4 — Workshop Lifecycle Management Flow (RESCHEDULE OPERATION, ASYNCHRONOUS EVENT FAN-OUT)`, `§4 — Workshop Search & Cache-Aside Flow (Cache Invalidation)`                                                                               |
| **ADR Refs**        | ADR-006, ADR-013 (optimistic locking), ADR-016 (SWR cache invalidation on write), ADR-017 (RabbitMQ), ADR-018 (outbox), ADR-027 (notification fan-out)                                                                                                           |

### 2.4 `workshop-cancellation`

**Description:** Enables `ORGANIZER` users to cancel a `DRAFT` or `PUBLISHED` workshop. Terminal states (`COMPLETED`, `CANCELED`) are immutable and cannot be re-canceled. On cancellation, a `WorkshopCanceledEvent` is written to the transactional outbox, which is then externalized via RabbitMQ to: (1) the `search_sync` worker, which removes the workshop from the Elasticsearch index; (2) the `notifications` worker, which sends bulk notifications to all affected registered students. The Redis search cache key for this workshop must also be invalidated so stale cached results do not continue serving a canceled workshop. The Redis capacity counter key for the workshop is cleaned up. Registrations in `PENDING` or `CONFIRMED` state are transitioned to `CANCELED` as a downstream consequence triggered by the event.

| **Worker Modules**  | `search_sync` (remove from ES index via RabbitMQ), `notifications` (bulk email/push to affected students via RabbitMQ)                                                                                                  |
| **System Flow Ref** | `docs/system-design.md §4 — Workshop Lifecycle Management Flow (CANCEL OPERATION, ASYNCHRONOUS EVENT FAN-OUT)`, `§4 — Workshop Search & Cache-Aside Flow (Cache Invalidation)`                                          |

### 2.5 `workshop-lifecycle-sweeper`

**Description:** Implements two automated background jobs: (1) **Lifecycle Sweeper** — a cron running hourly that detects `PUBLISHED` workshops whose `ends_at` timestamp has passed and bulk-transitions them to `COMPLETED`, writing `WorkshopCompletedEvent` entries into the transactional outbox. These events are externalized via RabbitMQ to the `search_sync` worker for Elasticsearch de-listing. (2) **Capacity Reconciliation Job** — a cron running every 5 minutes that detects and corrects Redis counter drift versus ground-truth database capacity counts (`capacity - COUNT(CONFIRMED + PENDING)`), resetting the Redis counter and emitting a `capacity.drift.detected` metric via Micrometer whenever drift is detected. Neither job has a user-facing endpoint.

| **System Flow Ref** | `docs/system-design.md §4 — Workshop Lifecycle Management Flow (AUTOMATED LIFECYCLE SWEEPER)`, `docs/system-design.md §6 — Overbooking Prevention (Redis-DB Capacity Reconciliation Job)`                                                                |

## 3. Workshop Discovery & Search

> **Domain Description:** Covers the public-facing workshop catalog and full-text search capabilities. Implements the CQRS read model backed by Elasticsearch and the Stale-While-Revalidate (SWR) cache-aside pattern backed by Redis. The `search` Spring Modulith module serves as the CQRS read-side, while background `search_sync` workers maintain the Elasticsearch index. Cache invalidation is triggered by `WorkshopUpdatedEvent` and `WorkshopCanceledEvent` via the outbox → RabbitMQ flow. References the **Workshop Search & Cache-Aside Flow** in `docs/system-design.md §4`.

### 3.1 `workshop-catalog-browsing`

**Description:** Provides authenticated students and unauthenticated public users with paginated browsing of `PUBLISHED` workshops, with filtering by date range, location, and price range (free/paid). Catalog results are served from the PostgreSQL replica under eventual consistency semantics (non-critical browsing path per ADR-015). Individual workshop detail pages include full metadata: title, description, speakers (bios, avatars, LinkedIns, emails), schedule, location, capacity, available seats (derived from Redis atomic counter with DB fallback on cache miss), and price.

| Attribute           | Detail                                                                                                                                                                                                           |
| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `workshops` (primary — catalog and detail read use cases), `search` (listing queries), `shared/config` (Redis)                                                                                                   |
| **Worker Modules**  | None                                                                                                                                                                                                             |
| **System Flow Ref** | `docs/system-design.md §4 — Workshop Search & Cache-Aside Flow`                                                                                                                                                  |
| **ADR Refs**        | ADR-012 (Elasticsearch CQRS), ADR-015 (Replica routing for browsing), ADR-016 (SWR cache-aside)                                                                                                                  |
| **DB Tables**       | `workshops`, `workshop_speakers` (read from replica)                                                                                                                                                             |
| **Clients**         | Web                                                                                                                                                                                                              |
| **Key Constraints** | Cursor-based pagination (keyset) per `docs/api-standards.md`. Default page size 20, hard cap 100. Available seats from Redis counter; fallback to `capacity - COUNT(CONFIRMED + PENDING)` from DB on cache miss. |

### 3.2 `workshop-full-text-search`

**Description:** Provides a dedicated full-text search endpoint (`GET /api/v1/workshops/search?q={keyword}`) that queries the Elasticsearch CQRS read model. Implements the full Stale-While-Revalidate (SWR) cache-aside strategy with dual TTLs (soft TTL: ~5 min, hard TTL: ~24 h). ## 4. Workshop Registration

> **Domain Description:** Covers the high-concurrency workshop registration lifecycle from initial request through confirmation or failure, including distributed rate limiting, atomic capacity enforcement, schedule overlap detection, idempotency, QR code generation, and automated reconciliation. This is the most performance-critical domain in the system, designed to handle 12,000+ concurrent users within a 10-minute window. References the **Workshop Registration Flow** in `docs/system-design.md §4` and the protection mechanisms in `§6`.

### 4.1 `free-workshop-registration`

**Description:** Handles the end-to-end registration flow for free (`price = 0`) workshops. The flow: (1) enforces distributed Token Bucket rate limiting (Bucket4j + Redis); (2) atomically inserts the idempotency key (`PENDING`) — concurrent retries return the cached response immediately; (3) detects schedule overlap (existing `CONFIRMED`/`PENDING` registrations for the same student in the same time window via primary DB query); (4) performs atomic Redis `DECR` capacity pre-check (lock-free overbooking prevention, returns `409` if counter goes negative); (5) inserts the registration with `status = CONFIRMED` and `qr_payload`/`qr_signature`/`qr_issued_at` atomically in a single database transaction with the outbox event; (6) updates the idempotency key to `COMPLETED`. The `WorkshopRegisteredEvent` is written to `event_publication` in the same transaction, then externalized by the Spring Modulith Event Registry to RabbitMQ, where the `notifications` worker consumes it to send the confirmation email and in-app notification. Returns `201 Created` with the QR payload. The `Idempotency-Key` header (UUIDv4) is mandatory.

### 4.2 `paid-workshop-registration`

**Description:** Handles the registration flow for paid (`price > 0`) workshops. ## 5. Payment Processing

> **Domain Description:** Covers the Stripe payment gateway integration and the webhook-driven asynchronous payment confirmation flow. This domain is responsible for financial data integrity and exactly-once payment state transitions. QR generation on payment confirmation is owned by the `registrations` module.

### 5.1 `payment-webhook-handling`

**Description:** Implements a dedicated, publicly accessible (unauthenticated) `POST /api/v1/payments/webhook` endpoint that receives asynchronous payment outcome events from the Stripe gateway (e.g., `payment_intent.succeeded`, `payment_intent.payment_failed`). Authentication is performed exclusively via **HMAC-SHA256 webhook signature verification** using the Stripe signing secret stored in environment variables — never JWT. For `payment_intent.succeeded`, the handler atomically updates `payments` to `COMPLETED`, transitions `registrations` to `CONFIRMED`, sets `qr_payload`/`qr_signature`/`qr_issued_at` (the `PENDING` → `CONFIRMED` atomic transaction), inserts a `WorkshopRegisteredEvent` into the outbox (`event_publication`), and updates the idempotency key to `COMPLETED` — all in a single DB transaction. The endpoint **always returns `200 OK`** to prevent gateway retry floods; internal errors are logged to DLQ. Idempotency is guaranteed by the `UNIQUE` constraint on `payments.provider_payment_id` — retried webhooks with the same `provider_payment_id` find the record already in a terminal state and return `200 OK` immediately without reprocessing (per ADR-022).

## 6. On-Site Check-in & Attendance

> **Domain Description:** Covers the mobile-first offline check-in experience for `STAFF` users and the server-side attendance reconciliation. This domain operates under a **Zero-Trust offline model**: the mobile app verifies QR signatures locally using a cached RSA public key (PKI), queues scans in SQLite, and synchronizes batches to the server when connectivity is restored. Server-side reconciliation uses workshop-scoped bulk upserts to prevent N+1 queries and database-level unique constraints to deterministically handle concurrent double-scans. The `sync_id` (device-generated UUIDv4) stored in the `attendances` table and indexed by `(workshop_id, sync_id)` is the primary idempotency mechanism for offline sync, ensuring a retried sync batch never creates duplicate attendance records. Corresponds to the `attendances` Spring Modulith module (backend) and the React Native Mobile App. References the **Offline Check-in & Synchronization Flow** in `docs/system-design.md §4` and **Offline PKI & Cryptography** in `§5`.

### 6.1 `mobile-offline-checkin`

**Description:** Implements the complete React Native Mobile App experience for Check-in Staff: (1) **Online data download** — on login, the app fetches and caches assigned workshops and the current RSA public key into local SQLite (`mobile_assigned_workshops`, `mobile_public_keys`). The public key is returned as part of the `STAFF` login response (see `authentication-and-session-management`) and can also be refreshed on demand via `public-key-distribution`. (2) **Offline QR scanning** — the staff member selects an assigned workshop, scans student QR codes; the app verifies the RSA signature offline using the cached public key, generates a `sync_id` (UUIDv4 on device), and persists the record to `mobile_sync_queue` with `sync_status = PENDING`. Forged or invalid QR codes are dropped immediately with a local "Invalid Ticket" error and never written to the queue. (3) **Sync on connectivity** — when connectivity returns, the app POSTs the batch to the server and updates each SQLite record's `sync_status` from the `207 Multi-Status` response.

### 8.1 `ai-brochure-summarization`

**Description:** Implements the full PDF brochure upload-to-summary pipeline: **(1) Upload** — `ORGANIZER` uploads a PDF via `POST /api/v1/workshops/{id}/brochure` (multipart); the backend validates MIME type and file size, stores the PDF in MinIO/S3, creates a `workshop_brochures` record, creates an `ai_summary_jobs` record with `status = PROCESSING` (state machine: `PROCESSING` → `COMPLETED`/`FAILED`), and writes a `BrochureSummarizationRequestedEvent` to the transactional outbox — returning `202 Accepted` with the job ID. The `ai_summary_jobs` table tracks `attempts` (retry counter), `next_retry_at` (scheduled retry time for broker-backed backoff), `status` (`PROCESSING`/`COMPLETED`/`FAILED`), `result_text`, and `error_message` — all state transitions are driven exclusively by the `ai_processing` worker, never by the web client or backend directly. **(2) Worker Processing** — the `ai_processing` worker consumes the event from RabbitMQ (via outbox → Spring Modulith Registry → RabbitMQ path), fetches the PDF from MinIO/S3, extracts and chunks text locally using PDFBox (to bound payload size and prevent AI token-limit errors), and submits chunks to the external AI Summarization Service. On success, updates `ai_summary_jobs.status = COMPLETED`, `result_text`. On transient errors (HTTP 429, 5xx, timeout), increments `attempts`, sets `next_retry_at`, and retries with broker-backed exponential backoff. On max-retry exhaustion, marks `status = FAILED` (prevents zombie `PROCESSING` states) and routes to DLQ. **(3) Status polling** — Organizer polls `GET /api/v1/workshops/{id}/brochure/summary-job` for job status and retrieves the summary on completion.

### 10.1 `distributed-rate-limiting`

> **Status:** DONE

**Description:** Implements the application-level distributed Token Bucket rate limiter using **Bucket4j + Redis** in the Core Backend Monolith's HTTP filter layer. ### 10.4 `infrastructure-bootstrap-and-seed-data`

> **Status:** DONE
