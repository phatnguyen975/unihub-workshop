## 1. Identity & Access Management

> **Domain Description:** Covers all authentication, authorization, user lifecycle, and tenant provisioning concerns. Every other domain depends on the identity contracts (`iam/api`) exposed by this module. Corresponds to the `iam` Spring Modulith module in the Core Backend and the multi-layer RBAC enforcement described in `docs/system-design.md §5`.

### 1.1 `user-registration-and-identity-verification`

> **Status:** DONE

**Description:** Allows a new `STUDENT` to self-register on the platform. Upon registration (`POST /api/v1/auth/register`), the account is created with `is_active = false` (preventing login) and an OTP (6-digit numeric) is generated, stored as a SHA-256 hash in `user_verification_tokens` (`token_type = 'ACTIVATION_OTP'`), and sent via email. The system also validates the submitted email against the `student_directory` table to establish a verified identity link (`users.student_record_id`). Students without a `student_record_id` match can verify their account but are blocked from registering for workshops. A dedicated verification endpoint (`POST /api/v1/auth/activate`) allows users to submit the OTP to activate their account (`is_active = true`). A shared OTP resend endpoint (`POST /api/v1/auth/otp/resend`) allows requesting a new OTP if it expires or is lost. This is the only self-service account creation flow.

### 1.2 `authentication-and-session-management`

> **Status:** DONE

**Description:** Implements the complete authentication session lifecycle: login (`POST /api/v1/auth/login`) with email/password returning an RS256-signed JWT access token, a long-lived refresh token, and user profile data for immediate UI rendering; access token refresh (`POST /api/v1/auth/refresh`) using the refresh token (with rotation on each use); and secure logout (`POST /api/v1/auth/logout`) that revokes the JWT's `jti` claim in the Redis blacklist and invalidates the refresh token in PostgreSQL. Also enforces the mandatory first-login password change for accounts where `is_temporary_password = true` (returning `403 Forbidden` with error code `urn:unihub:error:temporary-password` to route users to the first-login reset flow in F-1.4). The JWKS endpoint (`/.well-known/jwks.json`) exposes the RSA public key for token verification by downstream services.

### 1.3 `public-key-distribution`

> **Status:** DONE

**Description:** Provides a dedicated, authenticated `GET /api/v1/auth/public-key` endpoint that returns the current RSA public key in PEM format. This endpoint is the explicit mechanism for the mobile app to refresh its cached public key on demand — for example, after a key rotation event that invalidates previously cached keys. Unlike the JWKS endpoint (which is used for JWT signature verification by downstream services), this endpoint is designed specifically for the mobile `STAFF` client and returns the key in the PEM format that the mobile app can directly store in `mobile_public_keys`. Key rotation invalidates all previously issued QR signatures; staff must fetch the new key on their next online session. Without this endpoint, the mobile app has no mechanism to recover from a key rotation while the app is already authenticated.

### 1.4 `password-reset`

> **Status:** DONE

**Description:** Provides two dedicated password modification flows for non-authenticated users: (1) **Forgot Password Flow:** A user submits their email via the shared OTP resend endpoint (`POST /api/v1/auth/otp/resend`); the system generates a 6-digit numeric OTP, stores its SHA-256 hash in `user_verification_tokens` (`token_type = 'PASSWORD_RESET_OTP'`) with a 15-minute TTL, and sends it via email. The user then submits `{ email, otp, newPassword }` directly to `POST /api/v1/auth/password/reset`, which atomizes verification and reset: validates the OTP, marks it `used_at`, updates the Argon2 password hash, revokes all active refresh tokens in Postgres, and blacklists active access token JTIs in Redis. (2) **First-Login Temporary Password Flow:** Provisioned `STAFF`/`ORGANIZER` and seeded root organizer accounts where `is_temporary_password = true` submit `{ email, currentPassword, newPassword }` to `POST /api/v1/auth/password/temporary`. Upon verification of the temporary password, the system updates the password hash, flips `is_temporary_password = false`, and immediately issues an active JWT access token, refresh token, and user profile so the user transitions seamlessly to their dashboard without an extra login step.

### 1.5 `organization-member-management`

> **Status:** DONE

**Description:** Enables `ORGANIZER` users to administer member accounts within their own organization. Organizers can list organization members (cursor-paginated, filterable by role `ORGANIZER`/`STAFF`/`STUDENT`, status `isActive`, and keyword search; the calling organizer is excluded from results) and view individual member details. Organizers can provision new `STAFF` accounts and invite additional `ORGANIZER` accounts within their organization under the Zero-Trust model (ADR-028), where the system generates an initial secure temporary password emailed directly to the new user with `is_temporary_password = true`. Organizers can also toggle the active status of an existing member (`is_active = true/false`); banning a member immediately invalidates all active refresh tokens in Postgres and revokes active access tokens in the Redis JTI blacklist. All managed members are strictly scoped to the same `organization_id` as the calling `ORGANIZER`. `STAFF` users provisioned here have no check-in privileges until explicitly assigned to a workshop via `workshop-staff-assignment`.

### 1.6 `workshop-staff-assignment`

> **Status:** DONE

**Description:** Enables `ORGANIZER` users to manage `STAFF` assignments for workshops they own, granting assigned staff the authority to perform QR code scanning and attendance synchronization. Staff members are internal user accounts with role `STAFF` stored in `users` and assigned via `workshop_assignments` (strictly distinct from external workshop presentation speakers in `workshop_speakers` managed in F-2.1). Organizers can query currently assigned staff for a workshop (`GET /api/v1/admin/workshops/{id}/staff`, allowed in any workshop status for historical audit). Staff availability queries (`GET /api/v1/admin/workshops/{id}/staff/available`), batch assignments (`POST /api/v1/admin/workshops/{id}/staff`), and single revocations (`DELETE /api/v1/admin/workshops/{id}/staff/{userId}`) strictly require the workshop to be in `PUBLISHED` status and prior to its start time (`now() < starts_at`). Available staff queries exclude staff with overlapping schedules from other active (non-`CANCELED`) workshops. Upon successful assignment or revocation, the system emits fine-grained integration events (`StaffAssignedToWorkshopEvent` per assigned staff member / `StaffRevokedFromWorkshopEvent`) via the transactional outbox (`shared/events`), and the `notifications` background worker consumes them to broadcast informational emails to the affected staff (including workshop title, schedule, and venue details). `STAFF` members can only check in at workshops they are explicitly assigned to — even within the same organization, an unassigned `STAFF` user receives `403 Forbidden` at check-in. Assignments are tracked in `workshop_assignments`.

### 1.7 `active-session-management`

> **Status:** DONE

**Description:** Provides authenticated users across all roles (`STUDENT`, `STAFF`, `ORGANIZER`) with the ability to view and revoke their active login sessions. Each row in `refresh_tokens` represents one active session and carries `device_info` (User-Agent / device name) and `ip_address` for identification. The JWT access token carries a `sid` (Session ID) claim linking to `refresh_tokens.id`. `GET /api/v1/auth/sessions` returns a cursor-paginated list of non-expired, non-revoked sessions with an `isCurrentSession` indicator computed via `sid`. `DELETE /api/v1/auth/sessions/{id}` revokes a specific session by setting `revoked_at` on the `refresh_tokens` row and blacklisting the corresponding access token's `jti` in Redis. `DELETE /api/v1/auth/sessions` (revoke-all) revokes all sessions belonging to the user except the caller's current session (preserved via `sid`). This feature enables users to detect and terminate unauthorized sessions — a standard security control made possible by the `device_info` and `ip_address` columns in `refresh_tokens`.

## 2. Workshop Lifecycle Management

> **Domain Description:** Covers the entire server-side management of workshops from creation through terminal states. This is the most complex domain in the system, involving strict state machine enforcement (`DRAFT` → `PUBLISHED` → `COMPLETED`/`CANCELED`), multi-tenant ownership checks, optimistic locking for concurrent edits, automated sweeper-based transitions, and the transactional outbox pattern for reliable event fan-out to Elasticsearch and notification workers. Corresponds to the `workshops` Spring Modulith module and the **Workshop Lifecycle Management Flow** in `docs/system-design.md §4`.

### 2.1 `workshop-creation-and-draft-management`

> **Status:** DONE

**Description:** Enables authenticated `ORGANIZER` users to create, browse, and manage workshops in `DRAFT` status (as well as monitor all workshops within their organization) via a unified Save Draft endpoint (`POST /api/v1/admin/workshops/drafts`), upload workshop and speaker media assets (`POST /api/v1/admin/workshops/media/upload`), view workshop details for editing/previewing (`GET /api/v1/admin/workshops/{id}`), list/filter organization workshops (`GET /api/v1/admin/workshops`), and hard-delete drafts (`DELETE /api/v1/admin/workshops/{id}`). On save, if `id` is null, a new draft is created; if `id` is provided, modified fields on the existing draft are updated under optimistic concurrency control (`version`). In `DRAFT`, most fields are optional (`description`, `cover_image_url`, `location`, `starts_at`, `ends_at`, `capacity`), allowing progressive drafting. The `slug` is automatically generated from `title` (supporting Vietnamese and English transliteration) and kept synchronized whenever `title` changes while in `DRAFT`. Media assets uploaded to MinIO are cleaned up when replaced on update or when a draft is deleted. The workshop is not visible to students, is not indexed in Elasticsearch, and generates no external domain events until published. Deletion of `DRAFT` workshops is the only hard-delete permitted in the system, cascading to attached speakers via `ON DELETE CASCADE`. When speakers are included (as an array), each speaker's email is validated, intra-request duplicate emails are rejected, and the system verifies that no speaker email overlaps with any other active (non-`CANCELED`, non-`DRAFT`) workshop in the same time window. A speaker overlap returns `422 Unprocessable Entity`. `GET /api/v1/admin/workshops` provides keyset cursor pagination (`cursor`, `size` with default 20, max 100) with filtering by `status` (`DRAFT`, `PUBLISHED`, `COMPLETED`, `CANCELED`), `priceType` (`FREE`, `PAID`), date range (`from`, `to`), search query `q` (case-insensitive substring match against `title`, `slug`, `location`, and `description`), and sorting (`sort=capacity,asc|desc`, `sort=price,asc|desc`, `sort=createdAt,desc|asc`, `sort=startsAt,asc|desc`, defaulting to `createdAt,desc`), reading directly from PostgreSQL Primary DB for read-after-write consistency, strictly scoped to `jwt.org`.

### 2.2 `workshop-publishing-and-update`

> **Status:** DONE

**Description:** Manages the `DRAFT` → `PUBLISHED` state transition (publishing via `PATCH /api/v1/admin/workshops/{id}/publish`) and the rules governing updates to an already `PUBLISHED` workshop (`PUT /api/v1/admin/workshops/{id}`). Modifications to workshops in `DRAFT` status belong exclusively to Feature 2.1 via `POST /api/v1/admin/workshops/drafts`. Publishing requires `version` in the request body (`{"version": integer}`) under optimistic concurrency control, validates mandatory fields (`title`, `starts_at`, `ends_at`, `location`, `capacity >= 1`), enforces temporal validity (`starts_at > now()` and `ends_at > starts_at`), and re-verifies that assigned speakers have no schedule conflicts with other active (`PUBLISHED`, `COMPLETED`) workshops. Publishing triggers a `WorkshopPublishedEvent` into the transactional outbox (`unihub.events::search`). This event is externalized by the Spring Modulith Event Registry to RabbitMQ queue `q.search`, and the `search_sync` background worker consumes it to index the workshop in Elasticsearch — this is the mechanism by which a newly published workshop becomes searchable. Once published, the update endpoint (`PUT`) strictly permits updating presentation and capacity expansion fields: `title` (which synchronizes `slug`), `description`, `cover_image_url` (with MinIO media cleanup for replaced assets), and `capacity` (where `capacity` cannot be reduced below the current `CONFIRMED` + `PENDING` registration count). All other fields are strictly prohibited in `PUT`: `starts_at` and `ends_at` must be altered exclusively via `workshop-rescheduling` (`PATCH /api/v1/admin/workshops/{id}/reschedule`, Feature 2.3) to trigger required resource collision checks and mass student notifications; `price` and `currency` are immutable once published; `status` must be altered only via dedicated state transitions (`publish`/`cancel`); `organization_id` is immutable; and `speakers` cannot be altered. Non-core updates via `PUT` emit a `WorkshopUpdatedEvent` (`unihub.events::search`) for Elasticsearch re-synchronization and Redis search cache invalidation, but never notify students. Optimistic locking (`@Version`) prevents lost updates from concurrent organizer edits, returning `409 Conflict` on version mismatch.

### 2.3 `workshop-rescheduling`

> **Status:** DONE

**Description:** Allows `ORGANIZER` users to reschedule a `PUBLISHED` workshop to a new future time slot via `PATCH /api/v1/admin/workshops/{id}/reschedule`. All workshops in the system are strictly offline. The reschedule endpoint is strictly restricted to `PUBLISHED` workshops that have not yet started (`now() < starts_at`) — attempting to reschedule a workshop that has already started, or is in `DRAFT`, `COMPLETED`, or `CANCELED` status returns `422 Unprocessable Entity`. Rescheduling requires `version`, `startsAt`, and `endsAt` in the request body (`{"version": integer, "startsAt": ISO-8601 UTC, "endsAt": ISO-8601 UTC}`) under optimistic concurrency control (`@Version`). All presentation (`title`, `description`, `coverImageUrl`), venue (`location`), pricing (`price`, `currency`), capacity (`capacity`), speaker (`speakers`), `status`, and `organization_id` fields are strictly prohibited in the request body (`422 Unprocessable Entity`). The system validates that the new time range is valid (`startsAt > now()` and `endsAt > startsAt`) and performs PostgreSQL-level resource collision checks: (1) **Location Collision Check:** Campus-wide (cross-organization) query ensuring the workshop's current venue `location` (matched case-insensitively and trimmed: `LOWER(TRIM(w.location)) = LOWER(TRIM(:location))`) is not already booked by another active (`PUBLISHED`, `COMPLETED`) workshop in the overlapping `[startsAt, endsAt]` window, excluding the current workshop (`id != :id`); (2) **Speaker Schedule Collision Check:** Re-verifies that none of the workshop's currently attached speakers have schedule overlaps with other active (`PUBLISHED`, `COMPLETED`) workshops in the new time window. On success, the workshop's `starts_at`, `ends_at`, `updated_at`, and `updated_by` are updated, `version` is incremented, and a `WorkshopRescheduledEvent` (carrying `workshopId`, `organizationId`, `title`, `slug`, `location`, `timezone`, `previousStartsAt`, `previousEndsAt`, `newStartsAt`, `newEndsAt`, `updatedAt`, `occurredAt`) is written to the transactional outbox (`unihub.events::workshop.rescheduled`). RabbitMQ routes this event to both `q.search` (for Elasticsearch re-sync by `search_sync` worker) and `q.notifications` (for mass student notifications by `notifications` worker). The Redis search cache key for affected queries is invalidated.

### 2.4 `workshop-cancellation`

> **Status:** DONE

**Description:** Enables `ORGANIZER` users to cancel a `PUBLISHED` workshop via `PATCH /api/v1/admin/workshops/{id}/cancel`. Cancellation requires `version` in the request body (`{"version": integer, "reason"?: string}`) under optimistic concurrency control, with an optional cancellation reason. All presentation, scheduling, capacity, and pricing fields are strictly prohibited in the request body (`422 Unprocessable Entity`). The client does not supply a `status` field; the backend strictly enforces the state transition (`PUBLISHED` → `CANCELED`) internally. Workshops in `DRAFT` status cannot be canceled; they must be hard-deleted via `DELETE /api/v1/admin/workshops/{id}` (Feature 2.1), and attempting to cancel a `DRAFT` returns `422 Unprocessable Entity`. Terminal states (`COMPLETED`, `CANCELED`) are immutable and cannot be re-canceled (`422 Unprocessable Entity`). Cancellation is strictly permitted only while the workshop has not concluded (`ends_at > now()`); attempting to cancel a workshop whose scheduled end time has already elapsed (`ends_at <= now()`) returns `422 Unprocessable Entity`. The API response returns `200 OK` with the canceled workshop representation including `canceledAt`. RabbitMQ routes the event to `q.search` (Elasticsearch de-listing by `search_sync` worker) and `q.notifications` (mass cancellation alert to registered students by `notifications` worker). Downstream event consumers purge the Redis search cache and capacity counter keys, transition registrations to `CANCELED`, and initiate student payment refunds (for PAID workshops) via asynchronous event consumption.

### 2.5 `workshop-lifecycle-sweeper`

> **Status:** DONE

**Description:** Implements two automated background jobs hosted within the Core Backend `workshops` module: (1) **Lifecycle Sweeper** — a configurable periodic cron (default every 5 minutes: `app.workshops.sweeper.cron`) that detects `PUBLISHED` workshops whose `ends_at` timestamp has passed (`ends_at <= NOW()`), bulk-transitions them to `COMPLETED`, invalidates/deletes their Redis capacity counter (`workshop:{id}:capacity`) post-commit (`AFTER_COMMIT`), and writes `WorkshopCompletedEvent` entries into the transactional outbox (`event_publication`). These events are externalized via RabbitMQ (`unihub.events::workshop.completed`) to the `search_sync` worker for Elasticsearch de-listing and search cache invalidation. To ensure safe execution in multi-node deployments behind Nginx, the job acquires a non-blocking distributed lock in Redis (`SET lock:sweeper:lifecycle true NX EX 240`) before execution. (2) **Capacity Reconciliation Job** — a configurable periodic cron (default every 5 minutes: `app.workshops.capacity-reconciliation.cron`) that scans active `PUBLISHED` workshops (`ends_at > NOW()`) and corrects Redis counter drift versus ground-truth database capacity counts (`Math.max(0, capacity - COUNT(registrations WHERE status IN ('CONFIRMED', 'PENDING')))`). To ensure safe execution in multi-node deployments behind Nginx, the job acquires a non-blocking distributed lock in Redis (`SET lock:sweeper:capacity-reconciliation true NX EX 240`) before execution. If a drift is detected or the Redis key is missing, it resets the Redis counter unconditionally (`SET workshop:{id}:capacity {groundTruth}`) and emits structured SLF4J warning logs (`[CAPACITY_DRIFT_DETECTED]`). Neither job exposes a user-facing HTTP endpoint.

> **Domain Description:** Covers the high-concurrency workshop registration lifecycle from initial request through confirmation or failure, including distributed rate limiting, atomic capacity enforcement, schedule overlap detection, idempotency, QR code generation, and automated reconciliation. This is the most performance-critical domain in the system, designed to handle 12,000+ concurrent users within a 10-minute window. ### 4.1 `free-workshop-registration`

> **Status:** DONE

**Description:** Handles the end-to-end registration flow for free (`price = 0`) workshops, along with student-facing registration and ticket query endpoints. The feature covers three capabilities:

1. **Free Workshop Registration (`POST /api/v1/registrations` with body `{"workshopId": UUID}`):** Executes in strict sequence: (1) distributed Token Bucket rate limiting enforced at the filter layer (Registration Tier: 5 tokens, refill 5 per 10s, returning `429 Too Many Requests`); (2) student profile verification gating via `iam::api` (`users.student_record_id IS NOT NULL`), rejecting unlinked student accounts with `403 Forbidden`; (3) 2-tier cache-aside idempotency check (Redis L1 + Primary DB L2 `idempotency_keys` table with mandatory `Idempotency-Key` header), where in-flight requests return `409 Conflict` (`Retry-After: 2`) and completed requests return instant cached `201 Created` replays; (4) workshop precondition validations via `workshops::api` (`WorkshopApi`): workshop must exist and be in `PUBLISHED` status (`404 Not Found` for non-existent or `DRAFT` status), must not have already started (`starts_at > now()`, returning `422 Unprocessable Content` if `starts_at <= now()`), must not be in terminal state (`COMPLETED`, `CANCELED` returning `422`), and must be free (`price == 0`, returning `422` directing to the paid checkout flow if `price > 0`); (5) duplicate registration and schedule conflict detection: returns `409 Conflict` if the student already holds an active registration (`status IN ('PENDING', 'CONFIRMED')`) for the same workshop, or `422 Unprocessable Content` if the student is registered for another active workshop whose schedule overlaps (`existing.starts_at < target.ends_at AND existing.ends_at > target.starts_at`); (6) Redis capacity pre-check: performs atomic lock-free `DECR workshop:{workshopId}:capacity` with self-healing lazy re-initialization from DB ground truth (`Math.max(0, capacity - COUNT(active registrations))`) on cache miss; if the resulting counter is negative, executes a compensating `INCR`, updates idempotency status to `FAILED`, and returns `409 Conflict`; (7) atomic database transaction: inserts registration with `status = CONFIRMED`, atomically populating `qr_payload` (canonical JSON: `{"registrationId", "workshopId", "studentId", "issuedAt"}`), `qr_signature` (Base64 string generated via server-side `SHA256withRSA` using `rsa.private-key`), and `qr_issued_at = now()`, inserts `WorkshopRegisteredEvent` into the transactional outbox (`event_publication`), and updates the idempotency key to `COMPLETED`; (8) post-commit hooks: externalizes `WorkshopRegisteredEvent` to RabbitMQ queue `q.notifications` via routing key `workshop.registered` for asynchronous email/push notification delivery by the `notifications` worker, and publishes `registration.updated` to the workshop Redis Pub/Sub channel (`unihub:stream:workshop:{workshopId}`) via `RealtimeEventPublisher` for real-time organizer dashboard SSE updates. Returns `201 Created` with the full registration representation including QR data.
2. **Student Registrations List (`GET /api/v1/registrations/me`):** Authenticated `STUDENT` retrieves a keyset-paginated list of their own registrations (`id`, `workshopId`, `workshopTitle`, `workshopSlug`, `startsAt`, `endsAt`, `location`, `status`, `priceAtRegistration`, `currency`, `createdAt`), filterable by `status`. Paged via universal keyset cursor (`?cursor={base64}&size={size}`) per `docs/api-standards.md`.
3. **Student Ticket Detail (`GET /api/v1/registrations/{id}`):** Authenticated `STUDENT` retrieves the complete ticket and check-in representation for a specific registration, including workshop metadata, registration status, `priceAtRegistration`, `currency`, and cryptographic check-in verification fields (`qrPayload`, `qrSignature`, `qrIssuedAt`). Enforces strict ownership verification (`registration.student_user_id == jwt.sub`), returning `403 Forbidden` if caller does not own the registration (`404 Not Found` if nonexistent).
4. **Worker Notification Delivery with Visual QR:** The `notifications` worker consumes `WorkshopRegisteredEvent` from RabbitMQ queue `q.notifications`, generates a scannable 2D QR barcode image (PNG) via ZXing (`com.google.zxing:core` / `javase`), embeds it as an inline MIME attachment (`cid:ticket-qr`) into the Thymeleaf confirmation email, records an in-app notification, and emits a real-time event to the student's SSE stream (`unihub:stream:user:{studentId}`).

### 5.1 `payment-webhook-handling`

> **Status:** DONE

> [!NOTE]
> Feature 5.1 is implemented concurrently with Feature 4.2 (`paid-workshop-registration`) within the same development cycle to provide a complete, end-to-end verifiable vertical slice from registration creation to payment confirmation, QR issuance, and notification delivery.

**Description:** Implements a dedicated, publicly accessible (unauthenticated) `POST /api/v1/payments/webhook` endpoint that receives asynchronous payment outcome events from the Stripe gateway (e.g., `payment_intent.succeeded`, `payment_intent.payment_failed`). ## 6. On-Site Check-in & Attendance

> **Domain Description:** Covers the mobile-first offline check-in experience for `STAFF` users and the server-side attendance reconciliation. This domain operates under a **Zero-Trust offline model**: the mobile app verifies QR signatures locally using a cached RSA public key (PKI), queues scans in SQLite, and synchronizes batches to the server when connectivity is restored. Server-side reconciliation uses workshop-scoped bulk upserts to prevent N+1 queries and database-level unique constraints to deterministically handle concurrent double-scans. The `sync_id` (device-generated UUIDv4) stored in the `attendances` table and indexed by `(workshop_id, sync_id)` is the primary idempotency mechanism for offline sync, ensuring a retried sync batch never creates duplicate attendance records. Corresponds to the `attendances` Spring Modulith module (backend) and the React Native Mobile App. References the **Offline Check-in & Synchronization Flow** in `docs/system-design.md §4` and **Offline PKI & Cryptography** in `§5`.

### 6.1 `mobile-offline-checkin`

> **Status:** READY

**Description:** Implements the complete React Native Mobile App experience for Check-in Staff: (1) **Online data download** — on login, the app fetches and caches assigned workshops and the current RSA public key into local SQLite (`mobile_assigned_workshops`, `mobile_public_keys`). ## 8. AI-Powered Brochure Summarization

> **Domain Description:** Covers the complete pipeline for uploading workshop PDF brochures and asynchronously generating AI-written summaries. This domain is fully decoupled from synchronous API flows via the transactional outbox and RabbitMQ — the core API returns `202 Accepted` immediately, and all heavy processing happens in the `ai_processing` background worker module. Corresponds to the `workshops` module (brochure upload endpoints, real-time push via SSE, and fallback polling) and the `ai_processing` worker module (full hexagonal pipeline). References the **Async AI Summarization Flow** in `docs/system-design.md §4`.

### 8.1 `ai-brochure-summarization`

> **Status:** DONE

**Description:** Implements the complete asynchronous PDF brochure upload and AI summarization pipeline: **(1) Upload & Validation** — Authenticated `ORGANIZER` uploads a PDF brochure via `POST /api/v1/admin/workshops/{id}/brochure` (multipart, form field `file`). The backend validates that the caller belongs to the organization owning the workshop (`workshop.organization_id == jwt.org`, returning `403 Forbidden` on mismatch, or `404 Not Found` if the workshop does not exist). The workshop must be in `DRAFT` or `PUBLISHED` status (`422 Unprocessable Entity` if `COMPLETED` or `CANCELED`). If a summary job is currently in `PROCESSING` status for this workshop, the upload is rejected with `409 Conflict` (`urn:unihub:error:conflict`) to prevent concurrent race conditions and duplicate AI inference costs. The backend validates MIME type `application/pdf`, magic byte header `%PDF-`, and file size (max 10 MB). It computes the file's SHA-256 checksum, uploads the PDF to MinIO bucket `unihub-brochures` under storage key `workshops/{workshopId}/brochures/{brochureId}.pdf`, and persists a `workshop_brochures` record. Any existing active brochure for the workshop is deactivated (`is_active = false`) while retaining historical records. It creates an `ai_summary_jobs` record with `status = PROCESSING` and writes a `BrochureSummarizationRequestedEvent` (`jobId`, `workshopId`, `brochureId`, `storageKey`, `organizerId`) to the transactional outbox (`unihub.events::ai.summarization`) before returning `202 Accepted` with `{ "jobId": UUID, "brochureId": UUID, "status": "PROCESSING", "createdAt": ISO-8601 }`. **(2) Worker Processing & AI Integration** — The `ai_processing` worker consumes the event from RabbitMQ queue `q.ai.summarization` (exchange `unihub.events`, routing key `ai.summarization`), fetches the PDF from MinIO bucket `unihub-brochures`, and extracts/cleans text locally using Apache PDFBox (ADR-026). If the PDF contains no extractable text (e.g. scanned image-only PDF), the worker immediately transitions `ai_summary_jobs` to `status = FAILED`, sets `error_message = "No extractable text found in PDF brochure"`, skips calling the external AI API, publishes an `ai.summary.failed` event to Redis Pub/Sub, and acknowledges (ACK) the broker message (non-retryable unrecoverable data error; skips broker retries and avoids DLQ pollution). When text is present, if sanitized text is $\le$ 50,000 characters, the worker directly invokes the external AI Summarization Service via `AiSummarizationPort` with a structured single prompt requesting a standardized Markdown summary (Objectives, Target Audience, Key Highlights/Agenda, Prerequisites/Speaker info); if text $> 50,000$ characters, text is chunked before summarization. Google Gemini API (configurable Flash series via `AI_GEMINI_MODEL`, e.g. `gemini-3.8-flash` via Google AI Studio Free Tier, with a mock adapter for local test environments) is used as the primary provider, protected by a Resilience4j circuit breaker (`aiProvider`). On success, the worker updates `ai_summary_jobs.status = COMPLETED`, `result_text = summary`, `completed_at = now()`. On transient errors (HTTP 429 rate limit, 5xx, timeouts), the worker increments `attempts`, sets `next_retry_at`, and retries with broker-backed exponential backoff up to 3 attempts. Upon exhausting max retries (3 attempts), the worker transitions the job to `status = FAILED`, persists `error_message`, publishes an `ai.summary.failed` event to Redis Pub/Sub, and dead-letters the message without requeue to DLQ (`unihub.dlx::dlq`). **(3) Real-Time Push & Polling Fallback** — On job completion or terminal failure, the worker publishes a `RealtimeEvent` JSON envelope (`eventId`, `eventType = "ai.summary.completed"`, `timestamp`, `payload = { jobId, workshopId, resultText }`) or (`eventType = "ai.summary.failed"`, `payload = { jobId, workshopId, errorMessage }`) to Redis Pub/Sub channel `unihub:stream:user:{organizerId}`, pushed directly to the Organizer's active browser SSE stream (ADR-031) to render the summary dialog in real time without overwriting draft descriptions. The endpoint `GET /api/v1/admin/workshops/{id}/brochure/summary-job` is provided as a fallback for reconnecting clients, returning the latest summary job for the workshop's active brochure (scoped to `jwt.org`, returning `404 Not Found` if the workshop does not exist or if no brochure has been uploaded for the workshop, and `200 OK` with `{ jobId, brochureId, workshopId, status, resultText, errorMessage, attempts, completedAt, createdAt }` when present).

## 10. System Reliability & Infrastructure

> **Domain Description:** Covers the cross-cutting infrastructure features that enable the platform to meet its non-functional requirements: rate limiting to absorb traffic spikes, circuit breakers to isolate third-party failures, observability to detect and diagnose incidents, and the infrastructure bootstrap that seeds initial data and configures the runtime environment. ### 10.1 `distributed-rate-limiting`

> **Status:** DONE

**Description:** Implements the application-level distributed Token Bucket rate limiter using **Bucket4j + Redis** in the Core Backend Monolith's HTTP filter layer. Each authenticated user is assigned a bucket keyed by `jwt.sub`; unauthenticated endpoints use IP as the bucket key. Supports multi-tier path matching: **registration-tier** (tight limits for registration spikes), **auth-tier** (strict limits for login, password, and OTP endpoints to prevent brute-force and Argon2 CPU DoS), **stream-tier** (for SSE connections), and **default-tier** (fallback for all other endpoints). Nginx acts as a pure forwarding proxy and performs no rate limiting.

### 10.4 `infrastructure-bootstrap-and-seed-data`

> **Status:** DONE

**Description:** Implements the idempotent startup bootstrap process and ongoing maintenance jobs: **(1) Organization & Root Organizer Seeding** — a Spring Boot `ApplicationRunner` reads root organization definitions and initial `ORGANIZER` accounts from JSON arrays in environment variables (`.env`), checks the database for existing records using `INSERT ... ON CONFLICT DO NOTHING` (or equivalent existence check before insert), and creates only missing entries. This idempotency mechanism is critical because both Node 1 and Node 2 of the horizontally scaled backend will run `ApplicationRunner` on startup simultaneously — without it, concurrent seeds would produce duplicate organizations and accounts. Seeded root `ORGANIZER` accounts are created with `is_temporary_password = TRUE` to force a mandatory password change on first login (issuing an authenticated session directly to Dashboard), consistent with the zero-trust provisioning model (ADR-028). **(2) RSA Key Pair Setup** — `private.pem` and `public.pem` files in `resources/security/` are loaded at startup for JWT signing and JWKS endpoint exposure. **(3) Database Migration** — Flyway applies `V1__init_schema.sql` and all subsequent migrations strictly on startup, before any application beans initialize. Flyway runs **only on the Core Backend**; the Workers app must set `spring.flyway.enabled=false` to avoid migration conflicts when both apps start simultaneously against the same Neon database. **(4) TTL Cleanup Scheduler** — a scheduled job runs periodically in the Workers app (defaulting to every 6 hours via `TTL_CLEANUP_CRON`, configurable in `.env`) to purge expired records from `idempotency_keys`, `refresh_tokens`, and `user_verification_tokens` to prevent table bloat (per `docs/database-schema.md §1`). **(5) Primary/Replica DataSource Routing** — configures a routing `DataSource` (using `AbstractRoutingDataSource`) in **both** the Core Backend and the Workers app that inspects the active transaction's `readOnly` flag: `@Transactional(readOnly = false)` routes to the primary; `@Transactional(readOnly = true)` routes to the replica. This is the foundational mechanism that all ADR-015 routing requirements in every downstream feature depend on.

| **Worker Modules**  | `maintenance` (primary — TTL cleanup scheduler, service, and persistence adapter), `shared/config` (DataSource routing bean for workers; Flyway explicitly disabled)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **System Flow Ref** | `docs/system-design.md §5 — Account Provisioning & Security (Bootstrapping)`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **ADR Refs**        | ADR-008 (Flyway for DDL migrations + environment-driven seed data for idempotency), ADR-005 (RSA key pair, JWKS endpoint exposure), ADR-028 (`is_temporary_password = TRUE` for seeded organizer accounts), ADR-015 (primary-replica routing strategy — this feature provides the routing infrastructure all other features rely on)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Seeded root `ORGANIZER` accounts must have `is_temporary_password = TRUE`. Flyway must run before `ApplicationRunner`. ### 10.5 `real-time-event-streaming-hub`

> **Status:** DONE

**Description:** Implements the platform-wide real-time event streaming infrastructure using **Server-Sent Events (SSE) and Redis Pub/Sub** (ADR-031). Provides an authenticated, long-lived HTTP stream endpoint (`GET /api/v1/stream/events`) for web clients. Maintains active client connections in an in-memory `SseEmitterRegistry` in the Core Backend Monolith. To support stateless horizontal scaling across multiple Spring Boot nodes behind Nginx, this feature subscribes each node to Redis Pub/Sub channels (`unihub:stream:user:{userId}` and `unihub:stream:workshop:{workshopId}`). When any domain module or background worker publishes an event via `RealtimeEventPublisher`, Redis distributes the event to all backend instances; the node holding the recipient's active `SseEmitter` serializes and streams the event. Also implements an automated 15-second heartbeat scheduler (`: ping\n\n`) to prevent socket idle timeouts across intermediate proxies, and handles client disconnects cleanly via `onCompletion` / `onTimeout` callbacks to prevent socket leaks.

| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend Modules** | `shared/realtime` (primary — `SseEmitterRegistry`, `RealtimeEventPublisher`, `RedisRealtimeSubscriber`, `StreamController`), `shared/config` (Redis Pub/Sub configuration), `shared/security` (JWT authentication on stream handshake)                                                                                                                                     |
| **Worker Modules**  | None (workers publish events via Redis Pub/Sub or RabbitMQ; SSE streaming is hosted on backend)                                                                                                                                                                                                                                                                            |
| **System Flow Ref** | `docs/system-design.md §6 — Real-Time Event Distribution Architecture (Server-Sent Events & Redis Pub/Sub)`                                                                                                                                                                                                                                                                |
| **ADR Refs**        | ADR-005 (JWT RS256 for stream authentication), ADR-010 (Redis resilience), ADR-031 (SSE and Redis Pub/Sub for real-time streaming)                                                                                                                                                                                                                                         |

| **Clients**         | Web (all authenticated roles)                                                                                                                                                                                                                                                                                                                                              |
| **Key Constraints** | Stream endpoint requires valid JWT Bearer authentication. Connection must emit `: ping\n\n` every 15s. Nginx must have `proxy_buffering off;` and 24h timeouts for `/api/v1/stream/`. Client should use `@microsoft/fetch-event-source`. Connections must be evicted immediately on disconnect or timeout to avoid memory leaks. No persistent state stored in PostgreSQL. |
