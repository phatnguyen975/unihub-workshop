# Idempotency and Exactly-Once Design Quality Checklist

Run this checklist against any idempotency design before considering it ready to implement. Every item must pass.

## Applicability

- [ ] The operation genuinely mutates state and has real retry risk — this skill was not applied reflexively to a read-only path that needs no special design.
- [ ] If the operation "looks" naturally idempotent (e.g. a `PUT`-style write), every side effect it triggers was individually audited for its own idempotency — not just the primary write.

## Key Scope and Ownership

- [ ] The idempotency key's scope is stated explicitly (e.g. `(actor, key)` for client-facing endpoints, or the provider's own event/ message ID for webhook and consumer paths).
- [ ] The key is generated by the client (or, for webhooks/events, is the provider's own identifier) — not generated server-side on each attempt.
- [ ] The key represents one logical operation, not one HTTP attempt — a genuine retry reuses the same key.

## Atomicity

- [ ] The claim-and-record mechanism is a single atomic, database-enforced operation (e.g. an insert with a uniqueness constraint) — not a separate check step followed by a separate act step.
- [ ] This atomic claim happens in the same transaction as the first durable effect of the operation, not as a logically separate step that could succeed or fail independently of the operation itself.
- [ ] A concurrency-violation result (the key already exists) is handled by looking up and returning the existing record — never by re-attempting the underlying operation.

## Stored Record Completeness

- [ ] The stored record includes the actual response artifact to replay — status/code and body — not only a boolean or status enum.
- [ ] The stored record distinguishes between a completed (successful) outcome and a failed outcome, with each handled explicitly on retry.
- [ ] For failures specifically: each failure category has an explicit decision — replay the stored failure identically, or allow a fresh retry — rather than one blanket rule applied to every failure type without distinction.

## In-Flight Handling

- [ ] The case where a second request with the same key arrives while the first is still being processed (not yet completed or failed) has an explicit, defined response.
- [ ] That response is neither a silent duplicate execution nor an indefinite hang — it gives the caller a clear signal to wait and retry.

## Multi-Step Operations

- [ ] If the operation spans multiple steps (e.g. charge, then create a record, then notify), the idempotency key scopes the entire logical operation — not each step independently.
- [ ] If an earlier step succeeds and a later step fails, a retry of the whole operation does not re-execute the already-succeeded earlier step.

## Cross-Boundary Coverage

- [ ] Every additional async boundary this operation's flow crosses (a message queue, a webhook delivery to/from another system, a downstream consumer) was identified explicitly.
- [ ] Each of those boundaries has its own, separately designed idempotency/deduplication treatment — none of them is assumed to be covered by the idempotency design at the original entry point.

## TTL

- [ ] The TTL value is justified against this specific operation's realistic retry window (client type, network conditions, expected maximum legitimate retry delay) — not copied from an unrelated default.
- [ ] The TTL cleanup mechanism (a scheduled job, a database-level expiry feature, or equivalent) is identified, so expired records don't accumulate indefinitely.

## Testing

- [ ] A concurrent-retry test scenario is defined: two simulated simultaneous attempts with the same key, asserting exactly one underlying side effect occurred.
- [ ] A "completed-but-undelivered" scenario is covered: a retry against an already-completed record returns the original stored response without re-executing the operation.
- [ ] An in-flight scenario is covered: a retry against a record that is still processing receives the explicitly defined in-flight response, not a duplicate execution.

## Final Gate

- [ ] If this operation has a corresponding `API_CONTRACT.md` (per `api-contract-design`), its Idempotency Behavior section reflects this design exactly — not a simplified or inconsistent summary of it.
- [ ] Every assumption made about realistic retry behavior, key scope, or TTL was stated explicitly for human review — not silently decided without being surfaced.
