# UniHub Workshop - Registration & Payment Specs

## 1. Get Open Workshop List

Defines public and student access to published workshop listings using cache-aside reads.

| Field               | Details                                                                                                                                                                                                                                                                                                                                                                                        |
| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Get Open Workshop List                                                                                                                                                                                                                                                                                                                                                                         |
| Description         | Retrieves a paginated list of `PUBLISHED` workshops for browse/search traffic.                                                                                                                                                                                                                                                                                                                 |
| Actors              | Guest, Student                                                                                                                                                                                                                                                                                                                                                                                 |
| Main Flow           | 1. Validate pagination, sorting, and filter parameters.<br>2. Build a cache key from query parameters and check Redis (cache-aside).<br>3. On cache hit, return the cached page payload.<br>4. On cache miss, query the PostgreSQL Read Replica for `PUBLISHED` workshops only (exclude real-time `capacity_remaining`).<br>5. Store the result in Redis with a short TTL and return the page. |
| Error Scenarios     | - Invalid pagination or sort field returns 400.<br>- Database unavailable returns 503.                                                                                                                                                                                                                                                                                                         |
| Constraints         | - Only `PUBLISHED` workshops can be listed.<br>- Cache-aside via Redis is mandatory for read bursts.<br>- Cache misses must strictly route to the Read Replica to protect the Primary database from thundering herd traffic spikes.<br>- Real-time `capacity_remaining` is not fetched in this endpoint.                                                                                       |
| Acceptance Criteria | - Returned list contains only `PUBLISHED` workshops.<br>- Cache hit returns without database access.<br>- Pagination and sorting behave deterministically.                                                                                                                                                                                                                                     |

## 2. Get Workshop Detail

Defines public and student access to a single published workshop with real-time capacity.

| Field               | Details                                                                                                                                                                                                                                            |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Get Workshop Detail                                                                                                                                                                                                                                |
| Description         | Retrieves workshop details for a `PUBLISHED` workshop with exact `capacity_remaining`.                                                                                                                                                             |
| Actors              | Guest, Student                                                                                                                                                                                                                                     |
| Main Flow           | 1. Validate workshop ID format.<br>2. Query the primary PostgreSQL database for the workshop by ID with status `PUBLISHED`.<br>3. Read real-time `capacity_remaining` from the same row (bypass cache).<br>4. Return the workshop details payload. |
| Error Scenarios     | - Workshop not found or not `PUBLISHED` returns 404.<br>- Database unavailable returns 503.                                                                                                                                                        |
| Constraints         | - Must bypass cache to read real-time `capacity_remaining`.<br>- Only `PUBLISHED` workshops are visible.                                                                                                                                           |
| Acceptance Criteria | - Response contains current `capacity_remaining` from PostgreSQL.<br>- Non-published workshops are never returned.                                                                                                                                 |

## 3. Register Workshop

Defines the high-concurrency registration flow with locking, idempotency, and payment branching.

| Field               | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Use Case Name       | Register Workshop                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Description         | Creates a registration and reserves a seat with concurrency-safe logic.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Actors              | Student                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Main Flow           | 1. Enforce token bucket rate limiting via Redis.<br>2. Validate `Idempotency-Key`; if a cached success exists, return it immediately.<br>3. Validate workshop exists and is `PUBLISHED`.<br>4. Verify the student has no active registration for the workshop (status not `FAILED` or `CANCELED`); if present, return 409 Conflict.<br>5. Begin transaction and lock workshop row with `SELECT ... FOR UPDATE`.<br>6. If `capacity_remaining <= 0`, rollback and return 409 Conflict.<br>7. Decrement `capacity_remaining` and insert registration as `PENDING`.<br>8. If workshop is free, update registration to `CONFIRMED` and create the `WorkshopRegistered` outbox event in the same transaction.<br>9. Commit the transaction and store the idempotency success response.<br>10. If paid, call the external payment gateway under Resilience4j circuit breaker; on timeout or open circuit, trigger Capacity Compensation (Table 8) and return 503; on success, return payment session details. |
| Error Scenarios     | - Rate limit exceeded returns 429.<br>- Missing or invalid `Idempotency-Key` returns 400.<br>- Workshop not found or not `PUBLISHED` returns 404.<br>- Existing active registration returns 409.<br>- Capacity full returns 409.<br>- Payment gateway failure or circuit breaker open returns 503.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Constraints         | - `SELECT ... FOR UPDATE` is required to prevent overbooking.<br>- `capacity_remaining` must never drop below 0.<br>- A student can only have one active registration per workshop to ensure fairness.<br>- For free workshops, seat reservation and ticket issuance must be a single atomic database transaction.<br>- Idempotency responses must be cached for retries.<br>- Payment calls must be wrapped in Resilience4j circuit breaker.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Acceptance Criteria | - Seat allocation is concurrency-safe under burst traffic.<br>- Free workshops auto-confirm and emit outbox events.<br>- Paid workshops return a payment session and remain `PENDING` until webhook success.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## 4. Payment Webhook

Defines the gateway callback processing with signature validation and idempotent updates.

| Field               | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| :------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Payment Webhook                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Description         | Processes payment gateway callbacks to finalize registrations.                                                                                                                                                                                                                                                                                                                                                                                                   |
| Actors              | Payment Gateway                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Main Flow           | 1. Validate webhook signature and payload integrity.<br>2. Enforce idempotency using gateway transaction reference; if already processed, return 200.<br>3. Load the related registration and lock it for update.<br>4. If payment succeeded, update status to `PAID`, trigger QR Generation (Table 9), and emit outbox notification in the same transaction.<br>5. If payment failed, trigger Capacity Compensation (Table 8).<br>6. Return 200 to the gateway. |
| Error Scenarios     | - Invalid signature returns 401.<br>- Unknown transaction reference returns 404.<br>- Database unavailable returns 503.                                                                                                                                                                                                                                                                                                                                          |
| Constraints         | - Webhook processing must be idempotent per transaction reference.<br>- Signature validation is mandatory before any mutation.<br>- Success updates and outbox emission must be transactional.                                                                                                                                                                                                                                                                   |
| Acceptance Criteria | - Successful payments move registration to `PAID` and emit outbox events.<br>- Failed payments trigger capacity compensation exactly once.                                                                                                                                                                                                                                                                                                                       |

| Actors              | Student                                                                                                                                                                                       |

| Acceptance Criteria | - Student only sees their own registrations.<br>- Pagination behaves deterministically.                                                                                                       |

## 6. Get Ticket & QR

Defines student access to ticket details and QR payloads for confirmed registrations.

| Field               | Details                                                                                                                                                                                                                                                                        |
| :------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Get Ticket & QR                                                                                                                                                                                                                                                                |
| Description         | Returns ticket details and QR payload/URL for a registration.                                                                                                                                                                                                                  |
| Actors              | Student                                                                                                                                                                                                                                                                        |
| Main Flow           | 1. Validate registration ID format.<br>2. Resolve `user_id` from Security Context (`jwt.sub`).<br>3. Enforce ownership by matching `user_id`; mismatch returns 403.<br>4. Verify registration status is `CONFIRMED` or `PAID`.<br>5. Return ticket details and QR payload/URL. |
| Error Scenarios     | - Registration not found returns 404.<br>- Ownership violation returns 403.<br>- Status not eligible returns 409.                                                                                                                                                              |
| Constraints         | - Only `CONFIRMED` or `PAID` registrations are eligible.<br>- QR payload must be cryptographically signed.                                                                                                                                                                     |
| Acceptance Criteria | - Eligible registrations return ticket and QR details.<br>- Non-owners are blocked with 403.                                                                                                                                                                                   |

## 7. Cancel Registration

Defines student-initiated cancellations with ownership and timing enforcement.

| Field               | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Cancel Registration                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Description         | Cancels a registration and releases the seat back to the pool.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Actors              | Student                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Main Flow           | 1. Validate registration ID format.<br>2. Resolve `user_id` from Security Context (`jwt.sub`).<br>3. Enforce ownership by matching `user_id`; mismatch returns 403.<br>4. Verify registration status is `CONFIRMED` or `PAID`.<br>5. Verify workshop has not started (`start_time` strictly in the future).<br>6. In a single transaction, update registration to `CANCELED`, invoke Capacity Compensation (Table 8) using the same transaction with `SELECT ... FOR UPDATE` on the workshop row, and emit a `RegistrationCanceled` outbox event.<br>7. Return cancellation result. |
| Error Scenarios     | - Registration not found returns 404.<br>- Ownership violation returns 403.<br>- Status not eligible returns 409.<br>- Workshop already started or ended returns 409.                                                                                                                                                                                                                                                                                                                                                                                                               |
| Constraints         | - Cancellation is allowed only before workshop start time.<br>- Only `CONFIRMED` or `PAID` registrations can be canceled.<br>- Cancellation, seat compensation, and outbox emission must be executed as a single atomic transaction.                                                                                                                                                                                                                                                                                                                                                |
| Acceptance Criteria | - Status is updated to `CANCELED`, the seat is returned to `capacity_remaining`, and a confirmation outbox event is emitted.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## 8. Capacity Compensation

Defines internal recovery logic for failed payments and cancellations.

| Field               | Details                                                                                                                                                                                                                                                                                                                                                                                                              |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | Capacity Compensation (Internal)                                                                                                                                                                                                                                                                                                                                                                                     |
| Description         | Releases reserved capacity when a registration fails or is canceled.                                                                                                                                                                                                                                                                                                                                                 |
| Actors              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                      |
| Main Flow           | 1. Receive trigger with `registration_id` and failure reason.<br>2. Load registration and workshop using `SELECT ... FOR UPDATE`.<br>3. If status already `FAILED` or `CANCELED`, return with no change (idempotent).<br>4. Transition registration to `FAILED` or `CANCELED` as appropriate.<br>5. Increment `capacity_remaining` by 1, ensuring it does not exceed `capacity_total`.<br>6. Commit the transaction. |
| Error Scenarios     | - Registration or workshop not found returns 404 (internal error).<br>- Database unavailable returns 503.                                                                                                                                                                                                                                                                                                            |
| Constraints         | - Compensation must be idempotent per registration.<br>- Capacity increment must be transactional with status change.<br>- `capacity_remaining` must never exceed `capacity_total`.                                                                                                                                                                                                                                  |
| Acceptance Criteria | - Seats are released exactly once for failed or canceled registrations.<br>- Registration state reflects the final outcome.                                                                                                                                                                                                                                                                                          |

## 9. QR Code Generation & Allocation

Defines secure QR generation for confirmed or paid registrations.

| Field               | Details                                                                                                                                                                                                                                                                                                              |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Case Name       | QR Code Generation & Allocation (Internal)                                                                                                                                                                                                                                                                           |
| Description         | Generates and stores a signed QR payload and triggers delivery.                                                                                                                                                                                                                                                      |
| Actors              | Internal System                                                                                                                                                                                                                                                                                                      |
| Main Flow           | 1. Receive trigger for a `CONFIRMED` or `PAID` registration.<br>2. Generate a signed payload (for example, JWT with `workshop_id`, `user_id`, `registration_id`, and expiry).<br>3. Persist the QR payload or URL to the registration record.<br>4. Emit an outbox event for email delivery in the same transaction. |
| Error Scenarios     | - Registration not found returns 404 (internal error).<br>- Signing or storage failure returns 500.                                                                                                                                                                                                                  |
| Constraints         | - QR payloads must be cryptographically signed and tamper-evident.<br>- Outbox event must be persisted in the same transaction as QR storage.                                                                                                                                                                        |
| Acceptance Criteria | - QR payload is generated and stored for eligible registrations.<br>- Outbox event is emitted for email delivery.                                                                                                                                                                                                    |
