# UniHub Workshop - Users Specifications

This module defines authenticated profile management, organization ownership, and organizer-driven staff provisioning and account control. It preserves tenant boundaries, enforces organizer autonomy, and keeps all cross-module coordination event driven through the Spring Modulith event publication registry.

Any authenticated user with `isTemporaryPassword = true` is forbidden from accessing protected resources until the password is updated. The only allowed authenticated endpoints for such a user are Update Password and Logout.

## 1. Logout

| Field                   | Details                                                                                                                                                                                                                                                                                                      |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Logout                                                                                                                                                                                                                                                                                                       |
| **Description**         | Revoke refresh capability and end the authenticated session.                                                                                                                                                                                                                                                 |
| **Actors**              | Student, Organizer, Staff                                                                                                                                                                                                                                                                                    |
| **Main Flow**           | 1. The system accepts the refresh token input.<br>2. The system validates the token format and signature.<br>3. The system extracts the jti claim and the remaining lifetime.<br>4. The system adds the jti to the Redis blocklist with the remaining lifetime.<br>5. The system returns a success response. |
| **Error Scenarios**     | - Missing token returns HTTP 400.<br>- Invalid token format returns HTTP 400.                                                                                                                                                                                                                                |
| **Constraints**         | - The blocklist lifetime must match the refresh token expiry.<br>- Logout must be idempotent for the same jti.<br>- Only the jti claim is stored in the blocklist.                                                                                                                                           |
| **Acceptance Criteria** | - Blocklisted jti values cannot be used for refresh.<br>- Repeating logout for the same jti does not fail.                                                                                                                                                                                                   |

## 2. Refresh Token

| Field                   | Details                                                                                                                                                                                                                                                                                                                          |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Refresh Token                                                                                                                                                                                                                                                                                                                    |
| **Description**         | Renew access for an authenticated session using refresh credentials.                                                                                                                                                                                                                                                             |
| **Actors**              | Student, Organizer, Staff                                                                                                                                                                                                                                                                                                        |
| **Main Flow**           | 1. The system validates the refresh token structure and signature.<br>2. The system checks the revocation list.<br>3. The system verifies that the user exists and remains active.<br>4. The system issues a new access token and optionally rotates the refresh token.<br>5. The system returns the new tokens and role claims. |
| **Error Scenarios**     | - Missing or invalid refresh tokens return HTTP 401.<br>- Revoked refresh tokens return HTTP 401.<br>- Expired refresh tokens return HTTP 401.<br>- A user that cannot be found or is not active returns HTTP 403.                                                                                                               |
| **Constraints**         | - Refresh tokens must be trackable for revocation.<br>- Rotation invalidates the previous token when rotation is enabled.                                                                                                                                                                                                        |
| **Acceptance Criteria** | - A valid refresh token returns a new access token.<br>- A revoked refresh token is rejected.<br>- Rotation invalidates the prior token.                                                                                                                                                                                         |

## 4. Get My Profile

| Field                   | Details                                                                                                                                                                                                               |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Get My Profile                                                                                                                                                                                                        |
| **Description**         | Return the authenticated user's profile record scoped to the current identity.                                                                                                                                        |
| **Actors**              | Student, Organizer, Staff                                                                                                                                                                                             |
| **Main Flow**           | 1. The system resolves the caller identity from the security context.<br>2. The system loads the user record by the resolved user identifier.<br>3. The system returns only the allowed profile fields for that user. |
| **Error Scenarios**     | - Unauthorized access returns HTTP 401.<br>- A missing user record returns HTTP 404.                                                                                                                                  |
| **Constraints**         | - The query must be strictly scoped to the caller identity.<br>- Cross user profile access is not allowed.<br>- The `USERS` table is the authoritative source for the profile record.                                 |
| **Acceptance Criteria** | - The response contains only the caller's profile data.<br>- Non authenticated requests are rejected.                                                                                                                 |

## 4. Update My Profile

| Field                   | Details                                                                                                                                                                                                                                                                   |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Update My Profile                                                                                                                                                                                                                                                         |
| **Description**         | Update permitted profile attributes for the authenticated user.                                                                                                                                                                                                           |
| **Actors**              | Student, Organizer, Staff                                                                                                                                                                                                                                                 |
| **Main Flow**           | 1. The system resolves the caller identity from the security context.<br>2. The system validates the submitted name and phone fields.<br>3. The system updates the user profile only for the resolved user identifier.<br>4. The system returns the updated profile data. |
| **Error Scenarios**     | - Unauthorized access returns HTTP 401.<br>- Invalid input returns HTTP 400.<br>- A missing user record returns HTTP 404.                                                                                                                                                 |
| **Constraints**         | - Only profile fields such as name and phone are mutable.<br>- Role and password changes are not allowed in this endpoint.<br>- The `USERS` table stores the profile row.<br>- The email and student ID fields cannot be updated.                                         |
| **Acceptance Criteria** | - Updates apply only to the caller's profile.<br>- Restricted fields are never modified.                                                                                                                                                                                  |

## 5. Change Password

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                    |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Change Password                                                                                                                                                                                                                                                                                                                                                            |
| **Description**         | Allow the authenticated user to replace their password and invalidate prior refresh sessions.                                                                                                                                                                                                                                                                              |
| **Actors**              | Student, Organizer, Staff                                                                                                                                                                                                                                                                                                                                                  |
| **Main Flow**           | 1. The system validates the current password and the new password.<br>2. The system verifies the current password against the stored hash.<br>3. The system hashes the new password with BCrypt and updates the `USERS` table.<br>4. The system sets `isTemporaryPassword` to `false`.<br>5. The system revokes existing refresh tokens according to token revocation policy.<br>6. The system returns the updated account state, including `isTemporaryPassword = false`. |
| **Error Scenarios**     | - Current password mismatch returns HTTP 401.<br>- A weak password returns HTTP 400.<br>- Unauthorized access returns HTTP 401.<br>- Any authenticated user with `isTemporaryPassword = true` is rejected from protected resources other than Update Password and Logout with HTTP 403.                                                                                                                                                                                                                                            |
| **Constraints**         | - Passwords must be strongly hashed with BCrypt.<br>- Refresh tokens must be revoked after a successful change.<br>- The `USERS` table is the source of truth for password state.<br>- A successful password update must persist `isTemporaryPassword = false` in the `USERS` table and clear the forced-change restriction.                                                                                                                                                                                          |
| **Acceptance Criteria** | - The password is updated and the old password no longer authenticates.<br>- `isTemporaryPassword` is cleared after the change and the response confirms `isTemporaryPassword = false`.                                                                                                                                                                                                                                      |

## 6. Create Organization

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                      |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Create Organization                                                                                                                                                                                                                                                                                                                                                                          |
| **Description**         | Create an organization owned by the authenticated organizer.                                                                                                                                                                                                                                                                                                                                 |
| **Actors**              | Organizer                                                                                                                                                                                                                                                                                                                                                                                    |
| **Main Flow**           | 1. The system validates the organization input.<br>2. The system creates a new organization record in the `organizations` table.<br>3. The system assigns the authenticated organizer as the organization owner.<br>4. The system publishes an organization created event through the Spring Modulith event publication registry.<br>5. The system returns the created organization details. |
| **Error Scenarios**     | - Validation failure returns HTTP 400.<br>- Unauthorized access returns HTTP 401.<br>- Non organizer access returns HTTP 403.                                                                                                                                                                                                                                                                |
| **Constraints**         | - Only an authenticated organizer can create an organization.<br>- Ownership is stored in the `organizations` table.<br>- All downstream work must use published events.                                                                                                                                                                                                                     |
| **Acceptance Criteria** | - The organization is persisted.<br>- The creation event is published.                                                                                                                                                                                                                                                                                                                       |

## 7. Update Organization

| Field                   | Details                                                                                                                                                                                                                                                                                                    |
| :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Update Organization                                                                                                                                                                                                                                                                                        |
| **Description**         | Allow an organizer to update only the organization they own.                                                                                                                                                                                                                                               |
| **Actors**              | Organizer                                                                                                                                                                                                                                                                                                  |
| **Main Flow**           | 1. The system resolves the authenticated organizer identity.<br>2. The system verifies that the requested organization is owned by that organizer.<br>3. The system applies allowed organization updates.<br>4. The system publishes an organization updated event through the event publication registry. |
| **Error Scenarios**     | - Non owner attempts return HTTP 403.<br>- Missing organization records return HTTP 404.<br>- Unauthorized access returns HTTP 401.                                                                                                                                                                        |
| **Constraints**         | - Ownership is required to mutate the `organizations` row.<br>- Organization updates must remain tenant bound.                                                                                                                                                                                             |
| **Acceptance Criteria** | - The organization is updated by the owner.<br>- The organization updated event is published.                                                                                                                                                                                                              |

## 8. Provision Internal Account

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Provision Internal Account                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Description**         | Create a staff account and automatically link it to the organizer's organization.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Actors**              | Organizer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Main Flow**           | 1. The system validates the payload for email, name, and staff role.<br>2. The system verifies that the caller is an organizer and resolves the organizer's organization identifier.<br>3. The system generates a cryptographically strong temporary password during account creation and stores the row in the `USERS` table.<br>4. The system assigns the staff user to the organizer's organization without allowing client supplied overrides.<br>5. The system publishes an internal account provisioned event that triggers delivery of the generated password to the staff member's email address.<br>6. The system returns the created record. |
| **Error Scenarios**     | - Duplicate email returns HTTP 409.<br>- Caller without organizer privileges returns HTTP 403.<br>- Invalid input returns HTTP 400.<br>- Organization not found returns HTTP 404.                                                                                                                                                                                                                                                                                                                                                             |
| **Constraints**         | - The Organizer must already own an organization.<br>- The system must automatically assign the Organizer's organization ID to the new staff record.<br>- Temporary passwords are system generated, cryptographically strong, one time use, and expire on first login.<br>- The system must trigger an internal event to send the generated password to the staff member's email address.<br>- The `USERS` table stores the staff account row.<br>- Accounts created with a temporary password must set `isTemporaryPassword = true` until the first successful password update.                                                                                                                                                                                                                                                                |
| **Acceptance Criteria** | - The staff record is created with the organizer's organization identifier.<br>- The provisioning event is published.<br>- The created account is marked with `isTemporaryPassword = true`.                                                                                                                                                                                                                                                                                                                                                                                                                         |

## 9. Manage Staff Account Status

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Manage Staff Account Status                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Description**         | Activate, lock, or deactivate a staff account owned by the organizer's organization.                                                                                                                                                                                                                                                                                                                                                                                |
| **Actors**              | Organizer                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Main Flow**           | 1. The system validates the requested status and action parameters.<br>2. The system verifies organizer authorization and organization ownership.<br>3. The system prevents the organizer from locking their own account.<br>4. The system updates the staff user's status in the `USERS` table using the `ACTIVE` and `LOCKED` states.<br>5. The system publishes a user status updated event and, when the account is removed from service, a deactivation event. |
| **Error Scenarios**     | - Invalid status returns HTTP 400.<br>- Unauthorized access returns HTTP 401.<br>- Non owner attempts return HTTP 403.<br>- A missing user record returns HTTP 404.                                                                                                                                                                                                                                                                                                 |
| **Constraints**         | - The account must belong to the organizer's organization.<br>- Status values are limited to `ACTIVE` and `LOCKED` for operational control.<br>- Deactivation must preserve retention and audit history.<br>- An Organizer is strictly prohibited from locking their own account.<br>- The system must verify the existing relationship in the `USERS` table before updating.<br>- All changes must be event published.<br>- Any account with `isTemporaryPassword = true` remains restricted to Update Password and Logout until the password is replaced.                                             |
| **Acceptance Criteria** | - The staff account status is updated within the organizer's tenant scope.<br>- The corresponding status event is published.<br>- Deactivation, when requested, is recorded without cross tenant leakage.                                                                                                                                                                                                                                                           |

## 10. Data Ownership Validation

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Data Ownership Validation                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Description**         | Middleware logic to enforce Multi-tenancy and Personal data boundaries.                                                                                                                                                                                                                                                                                                                                                                                            |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Main Flow**           | 1. The system loads the target resource after role validation.<br>2. The system identifies the organization ID and user ID from the security context.<br>3. For personal resources, the system compares the requester's ID with the resource owner identifier.<br>4. For organization resources, the system verifies that the resource's organization ID matches the requester's organization ID.<br>5. The system allows the mutation only when the values match. |
| **Error Scenarios**     | - Ownership mismatch returns HTTP 403.<br>- A missing resource returns HTTP 404.                                                                                                                                                                                                                                                                                                                                                                                   |
| **Constraints**         | - Ownership checks are required for organizer scoped mutations.<br>- Cross tenant access is not allowed.                                                                                                                                                                                                                                                                                                                                                           |
| **Acceptance Criteria** | - The owner can update the resource successfully.<br>- A non owner receives HTTP 403 Forbidden.                                                                                                                                                                                                                                                                                                                                                                    |
