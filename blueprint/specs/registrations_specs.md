# UniHub Workshop - Registrations Specifications

This module owns seat allocation, payment initiation, webhook-driven payment finalization, cancellation compensation, QR issuance, and timeout recovery. It is responsible for transactional consistency across registration state, payment records, and workshop seat capacity.

## 1. Reserve Seat

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Reserve Seat                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Description**         | Reserve a seat for a student with strict concurrency control to prevent overbooking.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Actors**              | Student, Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Main Flow**           | 1. The system validates the workshop identifier and the student identity.<br>2. The system starts a database transaction.<br>3. The system acquires a pessimistic row-level lock by executing a `SELECT FOR UPDATE` operation on the target workshop row in the `workshops` table.<br>4. The system checks `capacity_remaining` and rejects the request when no seat is available.<br>5. The system MUST check whether the student already holds a `PENDING` or `CONFIRMED` registration for ANY other workshop whose scheduled `start_time`/`end_time` overlaps the target workshop (closed-open interval `[start_time, end_time)`). If such an overlapping registration exists the system MUST abort and return HTTP 409 Conflict.<br>6. The system decrements `capacity_remaining` in the `workshops` table and creates a new registration row in the `registrations` table with status `PENDING`.<br>7. The system commits the transaction and returns the registration identifier with the payment lifetime metadata. |
| **Error Scenarios**     | - The system returns HTTP 409 when no seats remain.<br>- The system returns HTTP 409 when a time-overlap with an existing `PENDING` or `CONFIRMED` registration is detected.<br>- The system returns HTTP 503 when lock acquisition times out.<br>- The system returns HTTP 400 when the request payload is invalid.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Constraints**         | - The system must use pessimistic locking to prevent overbooking across concurrent instances.<br>- The registration lifecycle must start with status `PENDING` in the `registrations` table.<br>- The seat decrement and registration insert must be atomic across the `workshops` and `registrations` tables.<br>- This module MUST NOT perform attendance reconciliation or check-in logic which belongs to the `attendances` module.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Acceptance Criteria** | - The reservation is created atomically with status `PENDING`.<br>- `capacity_remaining` is decremented exactly once.<br>- Overlapping registrations are prevented and result in HTTP 409.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

## 2. Initiate Payment

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                            |
| :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Initiate Payment                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Description**         | Create a payment intent for a pending registration and return checkout metadata.                                                                                                                                                                                                                                                                                                                                                   |
| **Actors**              | Student, Internal System                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Main Flow**           | 1. The system validates the registration identifier and checks that the registration has not expired.<br>2. The system verifies that the registration state is still eligible for payment initiation.<br>3. The system creates a payment intent with the provider and receives a provider transaction reference.<br>4. The system persists provider reference metadata for correlation and returns checkout details to the caller. |
| **Error Scenarios**     | - The system returns HTTP 410 when the registration has expired.<br>- The system returns HTTP 409 when the registration status is not eligible for payment initiation.<br>- The system returns HTTP 502 when the payment provider fails to create an intent.                                                                                                                                                                       |
| **Constraints**         | - The registration must remain non-final until webhook confirmation updates the `registrations` table.<br>- Payment correlation metadata must map to a unique provider transaction identifier for later writes to the `payments` table.<br>- The workflow must preserve consistency between `registrations` and `payments` data.                                                                                                   |
| **Acceptance Criteria** | - The payment intent is created successfully for eligible registrations.<br>- The provider reference is persisted for webhook correlation.<br>- Checkout details are returned to the caller.                                                                                                                                                                                                                                       |

## 3. Payment Webhook Handling

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Payment Webhook Handling                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Description**         | Process asynchronous provider notifications and finalize registration state changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Main Flow**           | 1. The system validates the webhook signature and extracts the provider transaction identifier.<br>2. The system performs idempotency checks using the provider transaction identifier and exits safely when the webhook was already processed.<br>3. The system loads the target registration and verifies payment amount and currency expectations.<br>4. Upon successful payment, the system creates a transaction row in the `payments` table before any registration status transition.<br>5. The system transitions the registration in the `registrations` table to `CONFIRMED` after the payment row is persisted.<br>6. The system publishes payment success and seat finalization events.<br>7. On failed payment, the system writes a failed payment record in the `payments` table, sets the registration to `CANCELED`, and restores seat availability in the `workshops` table. |
| **Error Scenarios**     | - The system returns HTTP 401 when the webhook signature is invalid.<br>- The system returns HTTP 400 when amount or currency validation fails.<br>- The system returns HTTP 404 when the referenced registration cannot be found.<br>- The system returns HTTP 500 to trigger retry when transient processing errors occur.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Constraints**         | - Idempotency must be enforced using the provider transaction identifier, which maps to `provider_ref` in the `payments` table.<br>- The payment record insert in `payments` must occur before setting `registrations.status` to `CONFIRMED`.<br>- Registration and capacity updates must keep `registrations`, `payments`, and `workshops` tables consistent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Acceptance Criteria** | - Successful payment webhooks create a payment row and move the registration to `CONFIRMED`.<br>- Failed payment webhooks create a failed payment row, set registration to `CANCELED`, and restore capacity.<br>- Duplicate webhooks do not create duplicate side effects.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## 4. Get My Registrations

| Field                   | Details                                                                                                                                                                                                                                                                                                            |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Get My Registrations                                                                                                                                                                                                                                                                                               |
| **Description**         | Return the authenticated student's registration history with deterministic pagination.                                                                                                                                                                                                                             |
| **Actors**              | Student                                                                                                                                                                                                                                                                                                            |
| **Main Flow**           | 1. The system validates pagination and sorting parameters.<br>2. The system resolves the authenticated user identifier from the security context.<br>3. The system queries registration rows scoped to that user only.<br>4. The system returns a paged list of registrations with status and workshop references. |
| **Error Scenarios**     | - The system returns HTTP 401 when the caller is not authenticated.<br>- The system returns HTTP 400 when pagination parameters are invalid.                                                                                                                                                                       |
| **Constraints**         | - The query must be scoped strictly by user identifier in the `registrations` table.<br>- Pagination must remain deterministic for repeated requests.<br>- The response must not leak registration records owned by another user.                                                                                  |
| **Acceptance Criteria** | - The student sees only their own registrations.<br>- Pagination and sorting are stable across repeated calls.                                                                                                                                                                                                     |

## 6. Cancel Registration

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Cancel Registration                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Description**         | Cancel an eligible registration before workshop start and compensate workshop capacity.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Actors**              | Student                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Main Flow**           | 1. The system validates the registration identifier.<br>2. The system resolves the authenticated user identifier and verifies ownership.<br>3. The system verifies that the registration status is `CONFIRMED`.<br>4. The system checks the linked workshop start time and confirms the workshop has not started.<br>5. The system updates `registrations.status` to `CANCELED`.<br>6. The system increments `capacity_remaining` in the linked row of the `workshops` table in the same transaction.<br>7. The system publishes a registration canceled event and returns the cancellation result. |
| **Error Scenarios**     | - The system returns HTTP 404 when the registration is missing.<br>- The system returns HTTP 403 when ownership validation fails.<br>- The system returns HTTP 409 when the registration status is not eligible for cancellation.<br>- The system returns HTTP 409 when the workshop has already started.                                                                                                                                                                                                                                                                                           |
| **Constraints**         | - Cancellation must be rejected after the workshop start time in the `workshops` table.<br>- The system must increment `capacity_remaining` in the `workshops` table upon successful cancellation.<br>- The status update in `registrations` and capacity update in `workshops` must be atomic.                                                                                                                                                                                                                                                                                                     |
| **Acceptance Criteria** | - The registration transitions to `CANCELED` when eligible.<br+>- Capacity is restored exactly once.<br+>- A cancellation event is emitted.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## 7. Capacity Compensation

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Capacity Compensation                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Description**         | Release reserved capacity for registrations that transition to `CANCELED` in an idempotent manner.                                                                                                                                                                                                                                                                                                                                                                        |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Main Flow**           | 1. The system receives a compensation trigger that references a registration identifier.<br>2. The system loads target rows from `registrations` and `workshops` using row-level locks.<br>3. The system exits without mutation when compensation was already applied.<br>4. The system applies the required registration outcome and increments workshop capacity with upper-bound validation.<br>5. The system commits the transaction and records completion metadata. |
| **Error Scenarios**     | - The system returns HTTP 404 when registration or workshop rows are missing.<br>- The system returns HTTP 503 when database operations fail transiently.                                                                                                                                                                                                                                                                                                                 |
| **Constraints**         | - Compensation must be idempotent per registration in the `registrations` table.<br>- Capacity changes in `workshops` must never exceed `capacity_total`.<br>- Compensation updates must remain transactionally consistent across `registrations` and `workshops`.                                                                                                                                                                                                        |
| **Acceptance Criteria** | - Seats are released exactly once per compensable registration.<br>- Registration outcome and capacity values remain consistent.                                                                                                                                                                                                                                                                                                                                          |

## 8. QR Code Generation and Allocation

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| :---------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | QR Code Generation and Allocation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Description**         | Generate and persist a signed QR payload for eligible registrations.                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Main Flow**           | 1. The system receives a trigger for an eligible registration state.<br>2. The system verifies that the registration status is `CONFIRMED`.<br>3. The system generates a signed QR payload (a JWT) that contains registration, user, and workshop identifiers with expiry metadata. The JWT MUST be signed using the backend's RSA Private Key with the `RS256` algorithm.<br>4. The system stores the QR payload reference in the `registrations` table.<br>5. The system publishes a downstream delivery event in the same transaction. |
| **Error Scenarios**     | - The system returns HTTP 404 when the registration cannot be found.<br>- The system returns HTTP 409 when the registration state is not eligible for QR issuance.<br>- The system returns HTTP 500 when signing or storage fails.                                                                                                                                                                                                                                                                                                        |
| **Constraints**         | - QR issuance is allowed only for `CONFIRMED` entries in `registrations`.<br> - The QR payload must be cryptographically signed and tamper evident.<br> - Persistence and event publication must be atomic for the `registrations` update.                                                                                                                                                                                                                                                                                                |
| **Acceptance Criteria** | - A QR payload is generated for eligible registrations.<br>- The payload reference is persisted and the delivery event is published.                                                                                                                                                                                                                                                                                                                                                                                                      |

## 9. Payment Timeout Sweeper

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Payment Timeout Sweeper                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Description**         | Process expired pending registrations and release reserved seats in concurrent-safe batches.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Main Flow**           | 1. The system runs a scheduled sweep at the configured interval.<br>2. The system selects expired registrations in status `PENDING` from the `registrations` table.<br>3. The system locks selected rows using `SELECT FOR UPDATE SKIP LOCKED` to enable safe multi-instance processing.<br>4. The system marks each expired registration as `CANCELED`.<br>5. The system triggers capacity compensation to restore seats in the `workshops` table.<br>6. The system commits the batch and continues until no expired rows remain. |
| **Error Scenarios**     | - The system returns HTTP 503 when a database failure prevents batch execution.<br>- The system skips currently locked rows and processes them in a later sweep cycle.                                                                                                                                                                                                                                                                                                                                                             |
| **Constraints**         | - The sweep must use `SELECT FOR UPDATE SKIP LOCKED` on the `registrations` table.<br>- Multi-instance workers must process expired rows without collision.<br>- State transitions in `registrations` and capacity restoration in `workshops` must remain consistent.                                                                                                                                                                                                                                                              |
| **Acceptance Criteria** | - Expired `PENDING` registrations are transitioned to `CANCELED`.<br>- Reserved seats are restored without duplicate processing across instances.                                                                                                                                                                                                                                                                                                                                                                                  |
