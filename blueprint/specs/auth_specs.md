# UniHub Workshop - Authentication Specifications

This module defines the unauthenticated entry points for onboarding, recovery, and session lifecycle management, along with the security boundary checks that protect authenticated resources. It also codifies the token, ownership, and rate limiting rules that all protected endpoints rely on.

Any authenticated user with `isTemporaryPassword = true` is forbidden from accessing protected resources until the password is updated. The only allowed authenticated endpoints for such a user are Update Password and Logout.

## 1. Login

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Login                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Description**         | Validate credentials and return access and refresh tokens for an authenticated session.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Actors**              | Guest                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Main Flow**           | 1. The system validates the email and password format and rejects malformed requests with HTTP 400.<br>2. The system looks up the user by normalized email.<br>3. The system rejects accounts that do not exist or are not active and does not reveal whether the account exists.<br>4. The system verifies the stored password hash using BCrypt.<br>5. The system returns a password-change-required response and a restricted token when the account has `isTemporaryPassword = true`.<br>6. The system issues a short-lived access token and a longer-lived refresh token with a unique `jti` claim.<br>7. The system returns `isTemporaryPassword` in the login response so the client can enforce the forced-change flow immediately.<br>8. The system updates the last login timestamp and resets failed login attempts.<br>9. The system returns the issued tokens and role claims. |
| **Error Scenarios**     | - Invalid credentials increment failed login counters and return HTTP 401.<br>- Accounts that are unverified or locked return HTTP 403.<br>- Accounts with `isTemporaryPassword = true` return HTTP 403 for any protected resource other than Update Password and Logout.<br>- Missing required input returns HTTP 400.<br>- Too many failed attempts trigger temporary lockout behavior or HTTP 429.                                                                                                                                                                                                                                                                                                                                                       |
| **Constraints**         | - The user must be active to sign in.<br>- Passwords must be stored and compared with BCrypt.<br>- The access token must have a short lifetime, the refresh token must have a longer lifetime, and the refresh token must include a unique `jti` claim.<br>- Failed attempts are tracked per email for throttling.<br>- Role claims are issued as plain strings (`STUDENT`, `ORGANIZER`, or `STAFF`) without the `ROLE_` prefix.<br>- Authenticated users with `isTemporaryPassword = true` must be blocked from all protected resources except Update Password and Logout until the password is replaced. |
| **Acceptance Criteria** | - Valid credentials return access and refresh tokens with role claims and `jti` values.<br>- The system updates the last login timestamp on success.<br>- Error responses do not expose which field was invalid.<br>- Brute force attempts are throttled or locked out.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## 2. Register

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| :---------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Register                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Description**         | Create a new account and start the verification flow.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Actors**              | Guest                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Main Flow**           | 1. The system validates the email, password, and name fields.<br>2. The system checks whether an active account already exists for the email address.<br>3. The system hashes the password using BCrypt.<br>4. The system creates a new user or updates an existing unverified user with the new details.<br>5. The system generates a 6-digit OTP and stores it in Redis with a 5-minute TTL.<br>6. The system publishes a verification event through the Spring Modulith event publication registry.<br>7. The system returns a generic success response. |
| **Error Scenarios**     | - A duplicate active email returns HTTP 409.<br>- Invalid input returns HTTP 400.<br>- Requesting a new OTP before the 60-second cooldown expires returns HTTP 429.<br>- Redis or event publication failures return HTTP 202 with retry scheduling or HTTP 503 when the failure is critical.                                                                                                                                                                                                                                                                |
| **Constraints**         | - Active user emails must be unique after normalization.<br>- The email must be normalized to lowercase before database insertion in the `USERS` table.<br>- Passwords must be hashed before persistence.<br>- OTPs must be single use and expire after 5 minutes.<br>- OTP requests are rate limited per email with a 60-second cooldown.<br>- Event publication must be written in the same transaction as user creation.                                                                                                                                 |
| **Acceptance Criteria** | - The user is stored as unverified.<br>- The OTP exists in Redis with the correct lifetime.<br>- The verification email event is published.                                                                                                                                                                                                                                                                                                                                                                                                                 |

## 3. Verify OTP

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Verify OTP                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Description**         | Validate a one-time code and apply the action associated with the selected intent.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Actors**              | Guest                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Main Flow**           | 1. The system validates the email, OTP, and intent values.<br>2. The system loads the OTP from Redis and compares it with the submitted value.<br>3. The system validates the user state required for the selected intent.<br>4. The system activates the account when the intent is `REGISTER`.<br>5. The system issues a temporary reset token when the intent is `RESET_PASSWORD`.<br>6. The system clears or resets the OTP failure counter when validation succeeds.<br>7. The system invalidates the OTP after successful use. |
| **Error Scenarios**     | - A missing or expired OTP returns HTTP 400.<br>- An OTP mismatch increments the failure counter and returns HTTP 401.<br>- Too many failed attempts invalidate the OTP and return HTTP 429 or HTTP 403.<br>- A user state that does not match the intent returns HTTP 409.<br>- An unsupported intent returns HTTP 400.                                                                                                                                                                                                             |
| **Constraints**         | - The OTP must be single use and deleted after validation.<br>- The reset token must be short lived and bound to the user and email.<br>- For the `RESET_PASSWORD` intent, the system must generate and store a record in the `password_reset_tokens` table upon successful verification.<br>- Failed OTP attempts must be tracked (max 5 attempts) to reduce brute forcing of the 6-digit code.                                                                                                                                     |
| **Acceptance Criteria** | - Register intent activates the user and removes the OTP.<br>- Reset password intent returns only a reset token.<br>- The OTP cannot be reused.                                                                                                                                                                                                                                                                                                                                                                                      |

## 4. Forgot Password

| Field                   | Details                                                                                                                                                                                                                                                                                                                               |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Forgot Password                                                                                                                                                                                                                                                                                                                       |
| **Description**         | Start the password recovery flow without revealing whether the account exists.                                                                                                                                                                                                                                                        |
| **Actors**              | Guest                                                                                                                                                                                                                                                                                                                                 |
| **Main Flow**           | 1. The system accepts the email input.<br>2. The system generates and stores an OTP in Redis with 5-minute TTL when the email exists and the account is active or locked.<br>3. The system publishes a reset email event through the Spring Modulith event publication registry.<br>4. The system returns a generic success response. |
| **Error Scenarios**     | - Invalid email format returns HTTP 400.<br>- Requesting a new OTP before the cooldown expires returns HTTP 429.<br>- Redis or event publication failure returns HTTP 202 with retry scheduling or HTTP 503 when critical.                                                                                                            |
| **Constraints**         | - The response must not reveal whether the account exists.<br>- The OTP must be single use and valid for 5 minutes.<br>- OTP requests are rate limited per email with a 60-second cooldown.                                                                                                                                           |
| **Acceptance Criteria** | - The response is identical for existing and non existing emails.<br>- Existing users receive the OTP and the notification event.                                                                                                                                                                                                     |

## 5. Reset Password

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                               |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Reset Password                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Description**         | Update credentials after verification and restore account access safely.                                                                                                                                                                                                                                                                                                                                                              |
| **Actors**              | Guest                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Main Flow**           | 1. The system validates the reset token and password confirmation.<br>2. The system verifies token ownership and validity against the `password_reset_tokens` table.<br>3. The system hashes the new password with BCrypt and updates the `USERS` table.<br>4. The system revokes all existing refresh tokens, resets failed attempts, unlocks the account, invalidates the used reset token, and sets `isTemporaryPassword` to `false`. |
| **Error Scenarios**     | - Invalid or expired reset tokens return HTTP 401.<br>- Password mismatch returns HTTP 400.<br>- A weak password returns HTTP 400.                                                                                                                                                                                                                                                                                                    |
| **Constraints**         | - The reset token must be short lived and single use, validated against the `password_reset_tokens` table.<br>- Passwords must be hashed with BCrypt.<br>- All refresh tokens are invalidated on success.<br>- A successful password update must persist `isTemporaryPassword = false` in the `USERS` table and clear the forced-change restriction for the account. |
| **Acceptance Criteria** | - The password update succeeds and old sessions are revoked.<br>- The reset token cannot be reused.<br>- The old password no longer authenticates.<br>- Locked accounts are unlocked after a successful reset.                                                                                                                                                                                                                        |

## 6. JWT and RBAC Middleware

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                             |
| :---------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | JWT and RBAC Middleware                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Description**         | Validate tokens and enforce role based access for protected operations.                                                                                                                                                                                                                                                                                                                                                             |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Main Flow**           | 1. The system extracts the `Authorization` header with the `Bearer` scheme.<br>2. The system validates the signature and expiration.<br>3. The system extracts the subject and role claims.<br>4. The system enforces the role rules required by the endpoint.<br>5. The system injects the user identity and authorities into the request security context.<br>6. The system forwards the authenticated request to the controller. |
| **Error Scenarios**     | - Missing tokens return HTTP 401.<br>- A malformed Authorization header, such as a missing Bearer prefix, returns HTTP 401.<br>- Invalid or expired tokens return HTTP 401.<br>- Insufficient roles return HTTP 403.                                                                                                                                                                                                                |
| **Constraints**         | - All protected endpoints must pass middleware validation.<br>- The role claim is the only source of role based access control.                                                                                                                                                                                                                                                                                                     |
| **Acceptance Criteria** | - A valid token grants access according to role rules.<br>- An invalid token never reaches the controller.<br>- A role mismatch returns HTTP 403.                                                                                                                                                                                                                                                                                   |

## 7. Rate Limiting

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                              |
| :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Rate Limiting                                                                                                                                                                                                                                                                                                                                                                                        |
| **Description**         | Protect APIs by enforcing per user or per IP token bucket limits.                                                                                                                                                                                                                                                                                                                                    |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                      |
| **Main Flow**           | 1. The system checks whether the request path is exempt and bypasses rate limiting when it is exempt.<br>2. The API gateway loads the route specific bucket configuration from Redis and checks the token bucket.<br>3. The system consumes a token and forwards the request when tokens remain.<br>4. The system rejects the request with HTTP 429 and rate limit headers when the bucket is empty. |
| **Error Scenarios**     | - Redis unavailable returns HTTP 503 or enters a degraded mode according to policy.<br>- An empty token bucket returns HTTP 429 with retry hints.                                                                                                                                                                                                                                                    |
| **Constraints**         | - Bucket4j uses Redis for distributed state.<br>- `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Retry-After` must be returned.<br>- Health checks and internal service traffic bypass the limiter.                                                                                                                                                                                  |
| **Acceptance Criteria** | - Requests above the limit return HTTP 429.<br>- Allowed requests are forwarded without delay.<br>- Rate limit headers are present.<br>- Exempt traffic is never throttled.                                                                                                                                                                                                                          |
