# UniHub Workshop - Notifications Specifications

This module is the centralized consumer for system events and manages delivery, templating, status tracking, retry handling, and operator notifications. It consumes published events from the other modules and routes them to delivery channels while keeping the state of every notification auditable and idempotent.

## Get Notification Status

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                              |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Get Notification Status                                                                                                                                                                                                                                                                                                                                              |
| **Description**         | Return the delivery history for notifications tied to a registration.                                                                                                                                                                                                                                                                                                |
| **Actors**              | Organizer                                                                                                                                                                                                                                                                                                                                                            |
| **Main Flow**           | 1. The system validates the registration identifier.<br>2. The system resolves the organizer identity from the security context.<br>3. The system verifies ownership against the related workshop.<br>4. The system queries the `notification_logs` table for the registration identifier.<br>5. The system returns the status history together with the timestamps. |
| **Error Scenarios**     | - A missing registration returns HTTP 404.<br>- Ownership violations return HTTP 403.<br>- Unauthorized access returns HTTP 401.                                                                                                                                                                                                                                     |
| **Constraints**         | - Access is limited to the workshop owner.<br>- Notification logs are read only and immutable.<br>- The `notification_logs` table stores the delivery history.                                                                                                                                                                                                       |
| **Acceptance Criteria** | - Status history is returned for valid registrations.<br>- Non owners cannot access the logs.                                                                                                                                                                                                                                                                        |

## Spring Modulith Event Publication

| Field                   | Details                                                                                                                                                                                                                                                                                                            |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Spring Modulith Event Publication                                                                                                                                                                                                                                                                                  |
| **Description**         | Externalize notification related event publications to RabbitMQ.                                                                                                                                                                                                                                                   |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                    |
| **Main Flow**           | 1. The system persists notification events in the Spring Modulith event publication registry within the originating transaction.<br>2. The system externalizes the pending publications to the appropriate RabbitMQ exchanges.<br>3. The system marks the publications as completed once externalization succeeds. |
| **Error Scenarios**     | - RabbitMQ unavailable returns a retryable failure.<br>- Database unavailable returns HTTP 503.                                                                                                                                                                                                                    |
| **Constraints**         | - Each event publication must be externalized at least once.<br>- Publication state transitions must remain transactional.<br>- The event publication registry is the source of truth for pending notifications.                                                                                                   |
| **Acceptance Criteria** | - Notification events are published to RabbitMQ.<br>- Event publication entries are marked completed.                                                                                                                                                                                                              |

## Transactional Email Consumer

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Use Case Name**       | Transactional Email Consumer                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Description**         | Send individual transactional emails using templates and provider APIs.                                                                                                                                                                                                                                                                                                                                                                     |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Main Flow**           | 1. The system consumes a notification message from RabbitMQ.<br>2. The system fetches the template through the template engine.<br>3. The system populates dynamic fields such as the student name, workshop title, and QR URL.<br>4. The system attaches the QR code when it is applicable.<br>5. The system calls the external email provider API.<br>6. The system records the result in `notification_logs` with status and timestamps. |
| **Error Scenarios**     | - A missing template returns a failed status.<br>- A provider API failure returns a retryable failure.                                                                                                                                                                                                                                                                                                                                      |
| **Constraints**         | - Template rendering must be deterministic.<br>- Notification logs must capture status transitions.<br>- The `notification_logs` table stores the delivery outcome.                                                                                                                                                                                                                                                                         |
| **Acceptance Criteria** | - Successful sends are logged as `SENT` or `DELIVERED`.<br>- Failures are captured with error details.                                                                                                                                                                                                                                                                                                                                      |

## Bulk Notification Consumer

| Field                   | Details                                                                                                                                                                                                                                                                              |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Bulk Notification Consumer                                                                                                                                                                                                                                                           |
| **Description**         | Process broadcast notifications and queue individual email jobs.                                                                                                                                                                                                                     |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                      |
| **Main Flow**           | 1. The system consumes a broadcast message from RabbitMQ.<br>2. The system queries all `CONFIRMED` or `PAID` attendees for the workshop.<br>3. The system enqueues individual notification jobs per attendee.<br>4. The system applies provider rate limiting and batching controls. |
| **Error Scenarios**     | - A missing workshop returns a failed status.<br>- A provider rate limit breach returns a retryable failure.                                                                                                                                                                         |
| **Constraints**         | - Bulk sends must respect provider rate limits.<br>- Each attendee must receive an individual notification job.<br>- The `registrations` table provides the attendee list.                                                                                                           |
| **Acceptance Criteria** | - Broadcast events produce per attendee jobs.<br>- Rate limits are honored without message loss.                                                                                                                                                                                     |

## Notification Template Engine

| Field                   | Details                                                                                                                                                                                                                                                                           |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Notification Template Engine                                                                                                                                                                                                                                                      |
| **Description**         | Render HTML templates with dynamic data for notifications.                                                                                                                                                                                                                        |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                   |
| **Main Flow**           | 1. The system selects the template based on the event type.<br>2. The system loads the template content from storage.<br>3. The system maps dynamic data into placeholders such as the student name, workshop title, and QR URL.<br>4. The system returns the rendered HTML body. |
| **Error Scenarios**     | - A missing template returns an internal error.<br>- A rendering failure returns an internal error.                                                                                                                                                                               |
| **Constraints**         | - Templates must be versioned and backward compatible.<br>- Rendering must be deterministic for the same inputs.                                                                                                                                                                  |
| **Acceptance Criteria** | - The rendered output contains the correct dynamic fields.<br>- Template selection remains consistent per event type.                                                                                                                                                             |

## Fallback, Retry and DLQ Strategy

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                        |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | Fallback, Retry and DLQ Strategy                                                                                                                                                                                                                                                                                                                                               |
| **Description**         | Retry failed notifications and route exhausted retries to the dead letter queue.                                                                                                                                                                                                                                                                                               |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                |
| **Main Flow**           | 1. The system detects provider failures such as timeouts or server failures.<br>2. The system retries delivery with exponential backoff and increments the retry count.<br>3. The system moves the notification to the dead letter queue after the maximum retry threshold is exceeded.<br>4. The system marks the notification as `PERMANENT_FAILURE` in `notification_logs`. |
| **Error Scenarios**     | - Retry enqueue failures return HTTP 500.<br>- Dead letter queue failures return HTTP 500.                                                                                                                                                                                                                                                                                     |
| **Constraints**         | - Exponential backoff is required for retries.<br>- Dead letter routing occurs after the maximum retry threshold is exceeded.<br>- Idempotency must be preserved through the notification identifier.                                                                                                                                                                          |
| **Acceptance Criteria** | - Transient failures are retried with backoff.<br>- Exhausted retries are routed to the dead letter queue and logged.                                                                                                                                                                                                                                                          |

## System Alert Consumer

| Field                   | Details                                                                                                                                                                                                                                                                                                                                                                          |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use Case Name**       | System Alert Consumer                                                                                                                                                                                                                                                                                                                                                            |
| **Description**         | Consume system level alerts and send summary emails to configured operational recipients.                                                                                                                                                                                                                                                                                        |
| **Actors**              | Internal System                                                                                                                                                                                                                                                                                                                                                                  |
| **Main Flow**           | 1. The system consumes a `CsvIngestionCompleted` message from RabbitMQ.<br>2. The system fetches the alert email template through the template engine.<br>3. The system populates dynamic fields such as the batch identifier, success count, and error count.<br>4. The system sends the email to configured operational recipients.<br>5. The system logs the delivery status. |
| **Error Scenarios**     | - A missing template returns an internal error.<br>- A provider API failure returns a retryable failure.                                                                                                                                                                                                                                                                         |
| **Constraints**         | - The delivery path must use the same retry and dead letter handling as other notification flows.<br>- The recipients must be configured, and no privileged operator role is required.                                                                                                                                                                                           |
| **Acceptance Criteria** | - Summary emails are delivered or retried according to policy.<br>- Delivery outcomes are recorded in logs.                                                                                                                                                                                                                                                                      |
