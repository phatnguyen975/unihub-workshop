## Critical Findings

### C-01 — FR-22 not implemented: `traceId` is never injected into the success-response envelope

**File:** `RequestLoggingFilter.java`, all future controllers (none yet exist)

**Impact:** FR-22 states: _"The `traceId` generated by the logging filter SHALL also be injected into the `metadata.traceId` field of every successful API response envelope."_ BR-05 states: _"The `traceId` used in MDC and log entries must be identical to the `metadata.traceId` value returned to the client."_ The current implementation populates the MDC with `traceId` then **clears it in the `finally` block after the response is committed** — but nothing ever reads the `traceId` from MDC and writes it into a response body. No global response advice, `HandlerInterceptor`, filter-level wrapper, or controller base class injects `metadata.traceId`. When future controllers return 2xx responses they will not contain `metadata.traceId`, breaking FR-22 and Scenario 11 end-to-end. The unit tests do not cover this acceptance criterion at all.

**Acceptance criteria not met:** Scenario 11 (FR-22, FR-19), BR-05.

### C-02 — `writeLog()` method has unreachable dead parameters and misleading signature

**File:** `RequestLoggingFilter.java` line 114

**Impact:** `writeLog(int status, String method, String uri, int httpStatus, long durationMs)` receives `method`, `uri`, and `durationMs` but never uses them. The call site at line 98 passes `status` as both the first and fourth argument (same variable, different parameter names). The log message `"API Request Completed"` contains no human-readable context of its own — every meaningful field relies on Logback reading MDC. If the appender or MDC key names are changed, the log entry becomes a context-free string. The misleading interface is a correctness hazard: future maintainers may attempt to use the parameters instead of MDC and produce subtly wrong output.

## Should-fix Findings

### S-02 — `createModuleDocumentation()` test generates filesystem side-effects during every `./gradlew test` run

**File:** `ModulithArchitectureTest.java` lines 18–26

**Impact:** `Documenter.writeDocumentation()`, `.writeModulesAsPlantUml()`, and `.writeIndividualModulesAsPlantUml()` write files to disk on every test run, dirtying the working tree. In CI pipelines using `git status --porcelain` this generates spurious untracked file changes. More importantly, this test asserts nothing — it is a generator, not a verifier. The task's acceptance criteria only require `ApplicationModules.verify()`. The documentation generator should be either removed from the test suite or annotated with `@Disabled` (run on demand).

### S-03 — `X-Forwarded-For` header is trusted unconditionally, enabling client IP spoofing in logs

**File:** `RequestLoggingFilter.java` lines 147–153

**Impact:** `getClientIp()` blindly trusts the `X-Forwarded-For` header as received by Tomcat. A client that fabricates `X-Forwarded-For: 1.2.3.4` before hitting Nginx will have `1.2.3.4` recorded as `clientIp` in every audit log entry, even though the real client IP is available via `request.getRemoteAddr()`. FR-18 mandates that `clientIp` reflects the observed client address. The correct approach is to trust `X-Forwarded-For` only when `RemoteAddr` belongs to a known trusted proxy CIDR (Nginx's internal Docker network).

### S-04 — `application-dev.yml` redundantly overrides `spring.application.name` from base config

**File:** `application-dev.yml` lines 6–8

**Impact:** `application.yml` already sets `spring.application.name: unihub-backend`. `application-dev.yml` repeats the same key with the same value. If the name is changed in `application.yml` but forgotten in `application-dev.yml`, dev-profile metrics will carry a different `application` tag than prod, silently breaking FR-05 / BR-07 tag consistency. Profile YAMLs should contain only overrides.

## Nit Findings

### N-01 — `writeLog()` parameters `method`, `uri`, `durationMs` declared but never read

**File:** `RequestLoggingFilter.java` line 114

The method body reads only `status`. The three unused parameters should be removed and the method simplified to `writeLog(int status)`.

### N-02 — `resolveLogLevel` is package-private for testability but this intent is not annotated

**File:** `RequestLoggingFilter.java` line 134

The Javadoc mentions it is package-visible for tests, but the access is simply the absence of `private`. A `@VisibleForTesting` annotation or `/* package */` comment would make the intent unambiguous and prevent an accidental future `private` addition.

### N-03 — `ObservabilityConfig.configureCommonTags()` is `public` solely for test accessibility

**File:** `ObservabilityConfig.java` line 61

The test class is in the same package, so package-private visibility would be sufficient without unnecessarily widening the API surface of a `@Configuration` class.

### N-04 — `ModulithArchitectureTest` lacks a class-level Javadoc

**File:** `ModulithArchitectureTest.java`

Given this is the primary architectural regression guard, a brief class-level comment explaining what `ApplicationModules.verify()` checks and which packages are in scope would help future developers who encounter a boundary violation error.

## FYI Findings

### F-01 — No rate-limiter exclusion for `/actuator/prometheus` yet (NFR, deferred)

The SPEC NFR states the Prometheus endpoint must be excluded from Bucket4j rate limiting. The rate limiter has not been implemented yet (belongs to a future feature). When it is added, it must explicitly exclude `/actuator/prometheus`. No action required in this feature.

### F-02 — `docs/api-standards.md` example `logger_name` value is stale

`docs/api-standards.md` shows `"logger_name": "com.unihub.api.RequestLoggingFilter"`, but the actual class is `com.unihub.workshop.shared.web.RequestLoggingFilter`. This is a documentation example discrepancy, not an implementation defect. The implementation uses the correct fully-qualified name. The docs example could optionally be updated for accuracy.

### F-03 — `spring-modulith-docs` is an implicit transitive dependency in the test classpath

**File:** `apps/backend/build.gradle`

`Documenter` (used in `ModulithArchitectureTest`) requires `spring-modulith-docs`. It currently resolves transitively through `spring-modulith-starter-test`, but is not declared explicitly. If the Modulith BOM is bumped and `spring-modulith-docs` is split into a separate artifact, the test will fail to compile silently.

## Axes with No Issues Found

### Performance

No database queries, collection loops with per-item I/O, or calls to external/slow dependencies are introduced. `RequestLoggingFilter` performs only in-memory MDC operations and `UUID.randomUUID()` per request — both O(1) with negligible overhead. No cache was introduced (no TTL/invalidation concern). **No performance findings.**

### Module Boundary (Design)

`shared/config` and `shared/web` are sub-packages of the root package and correctly scoped as internal shared infrastructure. `ModulithArchitectureTest.verifiesModularStructure()` passed with zero violations. All cross-class dependencies (`WebConfig` → `RequestLoggingFilter`, `ObservabilityConfig` → `MeterRegistry`) are intra-package or framework types. **No module boundary findings.**

### Infrastructure (T4, T5)

Nginx `location ~ ^/actuator` regex block is positioned before the catch-all `location /` block. Prometheus retention verified at 15d via `docker inspect`. Grafana `disableDeletion: true` is correctly set in camelCase (Grafana's YAML parser is case-insensitive at this field). **No infrastructure findings.**
